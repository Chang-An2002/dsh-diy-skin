# dsh-diy-skin

给 DeepSeek Harness Web GUI 做的「装修」插件：DeepSeek 品牌配色 + 不透明的弹出层 + 可自定义的背景图片 + 自定义界面颜色 + 角落常驻余额显示。

安装后**不会改动 app.asar 里任何官方源码**，卸载即完全还原。

## 它做了什么

1. **品牌配色** —— 一层可移除的 alias-token 覆盖层。
2. **弹出层不透明** —— 官方菜单默认是半透明毛玻璃，压在本插件的背景图上会看不清字。
3. **背景图片** —— 一张张**条目**：内置三张也是条目，全部可编辑、可删；也能自己加图，还能加一张**整图壁纸**（"添加壁纸"：铺满窗口、垫在所有图片下面、只保留一张，**也算在 8 张上限之内**）。**图片衬在整个界面所有文字之下**，所以调多不透明都不会盖住字（输入框那一条是唯一例外，见第 3 节的层序图）。左下角「背景」入口进编辑态后，**拖动移动、滚轮缩放、拖四角拉伸（对角固定、长宽比锁定）**；**右键任意一张图片**会在它旁边弹出这张图自己的控制（透明度、模糊、去白底及其参数）——只有这些，因为大小和位置是手的事。面板里同样只剩「手说不出来」的那些，另有两条「全部图片」批量滑杆；面板可拖动，底部显示占用与余量。编辑期间有一层透明隔离罩，不会误选中会话里的文字。
4. **界面配色自定义** —— 同一个面板的右栏，22 个旋钮，每个对应界面上一处（底色 / 侧栏 / 气泡 / 文字 / 按钮 / 链接 / 分隔线 / 代码块 / 状态色 / 两个角落按钮…）。十六进制输入 + 系统调色盘，浅色/深色分开编辑，「应用配色」可直接切换浅色/深色/跟随系统，自带 **7 套预设**（DeepSeek 品牌蓝 / 护眼绿 / 暖阳琥珀 / 紫罗兰 / 青瓷 / 墨玉黑 / 高对比）。鼠标停在旋钮名字上会说**这个颜色在哪里看得到**；那份实测依据在 [KNOB-REACH.md](KNOB-REACH.md)。除了这 22 个旋钮，插件还**常驻**接管了另外 30 多个应用别名（其他层级描边、各种悬停底色、悬浮按钮底、插件市场的勾选色、代码块家族、滚动条、文档选中色）——它们全部写成"跟随上面那些旋钮"的 `color-mix()`，所以改任何一个旋钮，整个界面（包括那些没有旋钮的角落）都会跟着走，不会留下蓝色鬼影。**除了那 7 套预设，你还可以把自己的调色板存成一套命名的方案**：「存为方案」把当前屏幕上整套 22 个旋钮的值存下来（不是"改过的那几个"的差量，所以回来时一模一样），方案排在预设后面，点一下应用；删除要点两次（第一次变成「确认删除」，旁边有「取消」），因为方案是你亲手起的名字，没有文件可以重新导入。
5. **去白底** —— 每张图一个勾选框。勾上之后用**从四边向内漫水填充**去掉白色背景（主体**内部**的白色会保留），两个旋钮**即时重算、即时预览**：**容差**（多白算背景）与**收边 / 扩边**（±3px，修白边或修被啃掉的地方）。**改哪个旋钮就存哪个旋钮**——参数记在图片上，下次打开还是你调好的样子；**取消勾选就回到原图**（连削掉的那份副本一起释放）。没有"确认"这一步：你要保留的本来就是你自己的照片，不该由一次点击来决定它还在不在。
6. **动图（GIF）** —— 可以直接当背景或贴纸：**原样保存，不缩放、不重编码**，所以动画保留。代价写在明处：动图的"去白底"开关是**禁用**的（去白底跑在 canvas 上，而 canvas 只有一帧，硬做会把动图变成静图）。一张 1600px 的静图约 0.15 MB，动图通常更大——读数条上能看到实际占用。
7. **角落余额** —— 常驻显示，单击刷新，**双击跳转充值页**。

配色到底能改哪些地方，见 [THEME-SURFACE.md](THEME-SURFACE.md)（那份清单由脚本从已安装的应用里读出来，不是凭印象写的）。

### 1. DeepSeek 品牌配色（主题层）

以一层可移除的 alias-token 覆盖层压在当前主题之上，通过官方扩展点
`ctx.theme.overrideTokens()` 注册，因此：

- 基础主题（light / dark / system）保持原样，只覆盖被点名的 token；
- 插件卸载时这一层被整体移除，自动还原成原色板；
- 亮色值 / 暗色值成对提供（这是该 API 的硬性要求，单值会导致切换配色后读不清）。

关键改动不是「加点蓝」，而是**从语义源头接管品牌色**。

这一点我第一版做错了：我直接覆盖 `--dsw-alias-button-primary-fill`，却绕过了它的上游。实际的依赖链是

```
--dsw-alias-brand-primary = 近黑 #0f1115（亮）/ 近白 #f9fafb（暗）
  ├── --dsw-alias-button-primary-fill = var(--dsw-alias-brand-primary)
  ├── --dsw-alias-brand-text
  └── （与 --dsw-alias-label-primary 同一族）
```

只改末端 token，整条链的其余部分仍是中性色，加上亮色底本来就是纯白——**结果就是"看不出来"**。现在改为覆盖语义源以及承载视觉面积最大的表面层：

| Token | 原来（亮 / 暗） | 现在（亮 / 暗） |
|---|---|---|
| `--dsw-alias-brand-primary` | 近黑 `#0f1115` / 近白 `#f9fafb` | 品牌蓝 `#4176e6` / `#5686fe` |
| `--dsw-alias-brand-text` | 近黑 / 近白 | `#4176e6` / `#7aaaff` |
| `--dsw-alias-button-primary-fill` | 继承 brand-primary | `#4176e6` / `#7aaaff` |
| `--dsw-alias-button-primary-hover` | 中性深灰 / 浅灰 | `#3a68d4` / `#93bcff` |
| `--dsw-alias-link` | 深蓝 / `#7aaaff` | `#2f62d6` / `#7aaaff`（提对比） |
| `--dsw-alias-bg-base` | 纯白 / 中性灰 `#151517` | 纯白 / **藏青** `#0d1424` |
| `--dsw-alias-bg-layer-2` | 纯白 / `#2c2c2e` | **蓝调** `#f4f8fe` / `#16203a` |
| `--dsw-alias-bg-layer-3` | 纯白 / `#1c2846` | **蓝调** `#eef4fd` / `#1c2846` |
| `--dsw-alias-label-primary` | `#0f1115` / `#f9fafb` | 藏青墨 `#101a33` / `#eef2fb` |
| `--dsw-alias-border-l2` | 中性黑 10% / 白 12% | 蓝调 `#1d4ed824` / `#ffffff20` |

底色仍保持纯白，是为了不牺牲正文对比度；蓝色集中在**表面层次**（layer-1/2/3）和**品牌源**上，这样主题才真的读起来是"蓝色界面"。共覆盖 50 个 token。

暗色模式整体从「中性灰」改成**藏青体系**，和角色形象的深藏青制服同一个色族。

品牌梯级取自 DSH 自带的静态色：`deepseek-500 #4176e6`、`400 #7aaaff`、`300 #b7c8fe`、`100 #e4edfd`、`50 #edf3fe`。

### 2. 弹出层改成不透明（第二层 token）

输入框左下角的 **「+」打开的是「命令菜单」**，它由 `ui-input-trigger` 渲染成一个 `MenuSurface`——**正好弹在左下角那张 Q 版背景图上**。而官方菜单材质是刻意做成毛玻璃的：

```css
.material { background: var(--dsw-menu-surface-fill);
            backdrop-filter: var(--dsw-menu-backdrop-filter); }
```

| Token | 官方值（亮 / 暗） |
|---|---|
| `--dsw-menu-surface-fill` | `#f8f9fa94`（**58% 不透明**）/ `#43454a73`（**45%**） |
| `--dsw-menu-backdrop-filter` | `blur(40px) saturate(150%)` |
| `--dsw-specific-menu` | `#f8f9faf0` / `#303136f0`（94%，仅缺蓝调） |

45% 不透明的深灰 + 40px 模糊底下压着一张浅色插画，就是"看不清内容"。修法是把它改成**完全不透明并关掉模糊**：

| Token | 现在（亮 / 暗） |
|---|---|
| `--dsw-menu-surface-fill` | `#fcfdff` / `#1a2540` |
| `--dsw-menu-backdrop-filter` | `none` / `none` |
| `--dsw-specific-menu` | `#fcfdff` / `#1a2540` |
| `--dsw-alias-menu-group-header-fill` | `#f7faff` / `#1f2b47` |

四点说明：

- 用**六位十六进制**（没有 alpha 通道）而不是 `rgba(...)`，这样"不透明"是格式上可断言的，测试里就是这么校验的。
- 这是**独立的第二层**（source = `dsh-diy-skin:material`），和品牌调色板可以分别移除。`overrideTokens` 支持多层叠加，后注册的按 token 覆盖。
- `--dsw-menu-surface-fill` **不是** `--dsw-alias-*` 名字，但一样能被覆盖：`validateOverrides()` 只要求值是 `{light, dark}` 成对字符串，名字以 `--` 开头即可；presenter 把 `active.tokens` 里每一项都写成 `body` 上的内联自定义属性。
- 菜单填充色比 `--dsw-alias-bg-layer-2` 略亮一档，保持"浮在表面之上"的层次感。

### 3. 背景图片（全部可编辑）

图层由一串**条目**组成，没有"内置"与"自加"之分：首次运行时那三张图会被**播种成普通条目**，和后来加的图享受同一套控件，也一样能删。

三张图播种时的初始值（就是原来那套固定几何换算过来的，`size` 是高度占视口百分比，`x`/`y` 是**中心点**位置）：

| 图片 | `x` | `y` | `size` | 原来的位置 |
|---|---|---|---|---|
| 全身立绘 | 90% | 80% | 46vh | 右下角，出血出画 |
| Q 版坐姿 | 27% | 90% | 23vh | 左下角，贴内容区左缘 |
| 表情包 | 80% | 12% | 15vh | 右上角，避开会话标题 |

所有图片都用同一套画法：`<img>` + 径向渐变蒙版（边缘向外淡出，避免生硬的矩形边框）+ `pointer-events: none`（不编辑时不接收点击）。**没有混合模式**——原因见下面"背景被两处系统表面盖住"那一节，这是被一个真实 bug 教出来的。

**图片以 data URI 内嵌在 bundle 里**，不是外部文件：DSH 的 web 服务只暴露插件的 bundle（`/plugins/...`），不会伺服包目录里的任意文件，所以 `<img src="../assets/x.webp">` 必然 404。内嵌同时也免疫 CSP 限制。条目里存的是 `builtin: 'chibi'` 这样的**引用**而不是那份 base64，所以三张图不会在 `localStorage` 里再存一遍。

**不再有任何手绘角色图形**：鲸尾标记与手绘半身像都已移除。

#### 左下角「背景」入口：鼠标直接拖

侧栏底部（余额芯片旁边）的 **「背景」** 按钮（图标是官方那条鱼，不是方块）打开编辑器：

| 操作 | 效果 |
|---|---|
| 拖动图片本身 | 移动。图片跟着指针走，**不会**跳到指针中心（抓取点被记下来了） |
| 在图片上滚动滚轮 | 缩放，一格 4vh |
| 拖**四个角**的小方块 | 拉伸。**对角固定不动**，长宽比锁定，所以不会变形 |
| 点空白处 | 取消选中（四个角的小方块只长在选中的那张图上） |
| 拖「全部图片」的两个滑杆 | 一次把所有图片的透明度 / 模糊改成同一个值 |
| 拖单张图的滑杆 | 精确微调这一张：大小 / 水平 / 垂直 / 透明度 / 模糊 |
| 拖面板标题栏 | 把面板挪开——它默认停在左下角，正好压着侧栏那一带 |
| 添加图片 | 选本地图片，可多选，最多 16 张（含壁纸） |
| 删除 / 清除全部 | |
| `Esc` 或右上 ✕ | 退出编辑 |

三条运算规则：

- **移动**：按下时记下指针在图片内部的偏移和 `getBoundingClientRect()`，之后每次移动用「指针位置 − 偏移」换算回中心点百分比。不需要知道渲染宽度。
- **缩放**：**对角是锚点**（这正是"四个角"而不是"四边中点"的原因——边上的把手只能改大小，角上的还隐含了"从哪儿长"）。于是中心必须跟着移动半个尺寸变化量。新高度取指针在「锚点→把手」对角线上的**投影**：`(dx·a + dy) / (a² + 1)`，其中 `a` 是宽高比。抓取那一刻这个投影恰好等于当前高度，所以**按下去不会跳**；而且整个计算只用模型里的数字（含 `aspect`），不需要量 DOM，画出来的和拖出来的不可能不一致。
- **长宽比从哪来**：模型只存高度、宽度自动，所以"渲染宽度"本来是不可知的。现在每张图把自己的 `aspect`（`naturalWidth / naturalHeight`）在图片解码完成时**记进条目里**（`onLoad`，值没变则不写），四个角的位置和缩放运算都由它推出来：
  `left: calc(30% + 40vh)` 这种——`%` 是视口宽、`vh` 是视口高，`calc` 会把两者都化成像素。

监听器一律挂在 `window` 而不是元素上——拖快了指针跑出图片也还在拖。

#### 编辑时会加一层透明隔离罩

进入编辑后，图层里会多出一个**全视口的透明罩**（`.dsd-shield`），它盖在整个应用之上、吞掉所有指针事件、并且 `user-select: none`。目的就是你说的那件事：**拖图片时不会误选中会话里的文字**。

四件事必须一起成立，否则罩子要么漏、要么反而把人困住：

1. **罩子 z-index 1，图片在编辑期间抬到 z-index 2** —— 图片必须盖在罩子上面，否则罩子会把拖动也一起吞掉。
2. **整个图层在编辑期间从 `z-index: 0` 抬到 `15`**。这条是踩出来的：会话面板自带正的 z-index，停在 0 的话罩子会**被会话面板盖住**，输入框仍然能点、会话文字仍然能选中——正是这个隔离罩要防的东西。`15` 高于应用内容，但低于官方浮层（`overlayLayer` 是 `20`）和模态（`1000+`），所以编辑期间官方菜单与弹窗仍然正常。
3. **退出方式**：面板右上 ✕，或 `Esc`。`Esc` 由**图层**注册而不是面板——面板是可能渲染失败的那一个（见下一条），图层不是。
4. **编辑期间滚轮不再滚动应用**（在 `window` 上 `preventDefault`，但放过面板自身的滚动）：否则滚轮会去滚一个被罩子挡住、又看不出在动的界面。

同时要知道：**编辑期间那个「背景」按钮也点不动了**。这是"整块应用被隔离"的直接含义，所以它不是开关；退出靠上面那两条路。

#### 一个把面板彻底搞没了的 React 陷阱

第一版这个编辑器上线后，点「背景」的结果是：**什么都没出现，但除了输入框以外全都点不动了，也退不出去**。

原因是一处 React 规则违反。`DecorEditor` 当时长这样：

```js
function DecorEditor() {
  const state = useDecorState();           // 2 个 hook
  if (state.editing !== true) return null; // ← 提前返回
  …
  React.useEffect(() => { … }, []);         // ← 第 3 个 hook 在返回之后
}
```

关闭状态下它只用 2 个 hook，打开状态下要用 3 个。React 明确拒绝这种更新——**"Rendered more hooks than during the previous render"**——渲染抛错、整个占用者子树被卸载，面板永远不出现。

而罩子为什么还在？因为它属于**另一个**组件（图层占用者，先注册、已经提交成功），不受影响。于是正好形成"罩子立起来了、面板没了、除了 z-index 更高的输入框之外全被挡住、`Esc` 也没注册"的僵局。

修法是把编辑会话的全部副作用都挪进**图层**：它整个生命周期都挂载着、没有提前返回，hook 数量在构造上就不可能变。

**更重要的收获是测试台补上了这个盲区。** 原来的假 React 只按索引存取 hook、不管数量变化，所以 22 项测试全绿却漏掉了这个必崩的 bug。现在渲染器会像真 React 一样比较每个组件两次渲染的 hook 数量，一变就抛：

```
hook count changed for DecorEditor: 2 -> 3. React rejects this update;
look for an early return above a hook.
```

我先把这个检查加进去、**跑出上面这行失败**确认诊断无误，再去改代码。这条检查对以后任何"提前返回写在 hook 之前"的改动都有效。

其它实现要点：

- **每张图是独立的盒子**，`<img>` 而不是背景图，因此**只给高度**、宽度按原图比例自动跟；`transform: translate(-50%,-50%)` 让它以中心点定位。
- 拖滑杆与拖图片都**即时生效**：所有组件订阅同一个 store，改完立刻重画，没有确认按钮。
- **「全部图片」的两个滑杆是"批量写入"而不是"倍数"**：拖一次，把值写给当时列表里的每张图，并记住滑杆停在哪儿。之后再单独调某一张，两者不会互相覆盖——因为你给那张图的是一个具体数字，不是相对量。这不只是设计选择，也是唯一能同时满足"统一控制"和"之后单独调整不受影响"的语义。
- 面板位置（拖过之后）和两个全局值都和图片列表存在同一个 key 里，重启后还在。
- 但**写盘是延后 300ms 的**（trailing debounce）：16 张图时整个 JSON 约 4 MB，拖动每秒能触发几十次变化，每帧序列化一次卡顿会非常明显。内存状态始终最新，只有 `localStorage` 写入在等；插件卸载时会把待写的改动立刻刷掉（`ctx.effect` 的清理函数里调 `decorStore.flush()`）。
- 图片**存在 `localStorage`**（key `dsd:background:v2`），和官方插件管理器记住安装源用的是同一个浏览器级存储，因此重启后仍在、且不写 profile。第一版用的 `dsd:background:v1` 会被**合并进来**而不是丢掉：它自己的图保留，内置三张按当时的 `showBuiltin` 决定要不要补回来。
- **选中时会先压缩**：长边超过 1600px 就经 `<canvas>` 重新编码成 webp（质量 0.82）。不这么做，一张手机照片就会把 `localStorage` 配额撑爆——配额失败会被捕获成面板里的一行提示，而不是抛出去打断渲染。
- 所有存储访问都**双重兜底**：拿不到 `localStorage`（不透明源）就退化成"能用但不持久"，配额溢出就提示。

#### 背景被两处系统表面盖住（以及"面板拖不回来"）

图片层是 `z-index: 0`，所以应用里**任何正值 z-index 的东西都画在它上面**。有两处正好如此，都被用户当场发现了。

**一、右上角三个窗口按钮下面那块。** 这块不是 DOM 画的，是 Electron 的 `titleBarOverlay`——原生矩形，永远在页面之上，CSS 碰不到它本身。但它的**颜色有来源**：桌面 preload 自己造了一个探针元素

```js
probe.style.cssText = 'position:fixed;visibility:hidden;pointer-events:none;'
  + 'background-color:var(--dsw-specific-sidebar-fill);color:var(--dsw-alias-label-primary)';
```

读它的 `background-color` / `color`（过一次 canvas 变成 `rgba()`），再通过 `dsh-desktop:windows-appearance` 交给主进程调 `setTitleBarOverlay`。所以只要让探针的底色变透明，那条通道会自己把透明送过去：

```css
span[style*='--dsw-specific-sidebar-fill']{background-color:transparent!important}
```

这里的 `!important` 是**必需的、也刚好够**：探针颜色是**行内样式**，按级联规则，作者样式表里的 `!important` 声明正好压过普通行内声明。preload 还监听 `head` 的子树变化以及 `body` 的 `style` / `data-ds-dark-theme` 属性，所以本插件往 `head` 插样式表的那一刻，它就会重新读取并上报。三个按钮的**符号颜色**来自同一个探针的 `color`（`--dsw-alias-label-primary`），没有改动——也就是说"主要文字"这个旋钮同时决定它们的深浅。

**二、输入框左右两侧那块。** 这条是应用自己的规则：

```css
.root[data-phase=active] .composerSeat{
  z-index:7; position:sticky; bottom:0;
  background:linear-gradient(180deg, color-mix(… 0%, transparent) 0px, var(--dsw-alias-bg-base) 36px);
}
```

`z-index:7` 让它盖在图片上，而那个渐变在 36px 之后变成不透明底色——它的用途是让正文滚到输入框下面时渐渐淡出，代价是把整个座位区（含输入框两侧）的图片都糊住。现在只清掉座位：

```css
[class*='composerSeat']{background:transparent!important}
```

**输入框本身没有动**（那是应用自己的 `.editor` 规则，不透明是对的），所以正文依然读得清。

**但清掉那块盖版会换来另一个问题**：正文滚到底部时，原来被盖版挡住的字就露出来了。而用户随后提出的更高的要求，正好把整个层序逼到了正确的位置上：

> 图片应该衬于界面上所有文字的下方，但保持输入框底下看不到正文却能看到图片。

### 现在的层序

一句话：**图片在最底下，应用画的一切都在它上面；输入框那一条是唯一的例外，由第二份图片补回来。**

```
   图片层  z-index: -1     ← 整个页面最底，应用画的所有东西都在它上面
   ──────────────────────────────────────────────────────────
   应用的文字、卡片、面板、侧栏、输入框……    ← 全都在图片之上
   ──────────────────────────────────────────────────────────
   输入框那一条：
     ① 遮挡层（不透明底色，只盖对话列底部）   z-index: 5    ← 在文字之上，把正文挡住
     ② 图片的第二份，裁到这一条               同一层，在 ① 之上   ← 于是图片照样看得见
```

**为什么必须画两份。** 图片在最底下就盖不住任何东西——这正是想要的；但"输入框底下看不到正文"要求有个东西**在文字之上**，而那个东西必然也在图片之上，会把图片挡住。一份图片没法同时满足这两件事，所以画两份：一份垫底，一份裁到那一条、盖在遮挡层上。两份走同一个定位函数（同一份 left/top/height/opacity/blur/mask），所以**逐像素重合**，那一条看上去和别处完全一样，区别只是字到这里为止。

**为什么把图片挪到最底下还需要两行额外的 CSS。** 应用有**两块铺满窗口的画布**填着不透明底色：应用外框和中间那一列。图片在它们之下就会被完全盖住，所以这两块必须变透明：

```css
[class*='frame']:has([class*='sidebarCol']){background:transparent!important}
[class*='centerCol']{background:transparent!important}
body{background-color:var(--dsw-alias-bg-base)}
```

两块画布之外还有**第三块**：会话列自己的 root。只把外面两块变透明时，图片会被它挡住，表现是"只有输入框那一条能看到图片"——这正是用户报的那个 bug。它用"里面有没有 composerSeat / composerHero"来认，因为 root 是这套代码里复用最多的类名。用 `:has([class*='sidebarCol'])` 而不是只写 `[class*='frame']`：好几个组件都有以 frame 结尾的类名（附件缩略图就是一个），只有应用外框里面才有侧栏列。这三个名字里**作者写的那一半**（frame、sidebarCol、centerCol）在重新打包后仍然稳定，前面那截哈希不稳定。

最后一行是**把"整体底色"这个旋钮搬到了文档画布上**：那两块画布的颜色本来就是 `--dsw-alias-bg-base`，它们透明之后这个颜色不能丢——它现在画在所有东西的最底下，于是图片边缘被蒙版淡出的地方露出来的仍然是用户选的那个底色。侧栏、卡片、输入框都保留自己的底色，所以"面板浮在壁纸之上"这个观感没有被破坏；想让壁纸也从它们后面透出来，把对应旋钮设成带 alpha 的十六进制值（比如 `#ffffff00`）即可，输入框接受 8 位。

**编辑时会临时反过来。** 图片在应用后面就永远收不到指针事件，也就拖不动。所以进入编辑时整层抬到 `z-index: 15`（在应用所有内容之上、在应用自己的浮层 20 与弹窗 1000+ 之下），由隔离罩负责让应用在这期间不可交互；退出编辑再沉回去。那一条的第二份此时不画，否则它会成为被拖动图片的一个不会动的影子。

顶部那 **44px** 是遮挡层上边缘的渐隐：从全透明到不透明。不然它会是一条横贯窗口的硬边，看起来像一道接缝。那一段之内正文渐渐消失，之外正常显示。

### 试过但不够的两个方案

两个都上线过，也都被用户当场否掉，留下的教训比结论值钱：

- **在座位上做磨砂**（`backdrop-filter: blur(12px)` + 40% 底色）：确实同时做到了"看不到正文"和"看到图片"，但那一层**在图片上面**，所以那一条里的图片又被糊了、又被冲淡了。教训：**任何画在图片这一侧的遮盖物，都会拿走图片的锐度或者强度。**
- **把不透明填充垫在图片下面**（再上一版）：图片保住了锐度，但代价是图片**必须**在应用内容之上，于是不透明度一调到 100% 就把所有文字盖住了。教训：**"文字永远在最上"和"图片永远不被挡"只能二选一——除非分层。**

### 混合模式那一课

遮挡层刚上线时，用户发现图片一进入那一条就**变成黑白**，而带子以外一切正常。原因是 `.dsd-bg` 一直带着 `mix-blend-mode: luminosity`。

它此前什么也没做，现在什么都能做了，因为它终于有了背景板：

- 混合只在**同一个层叠上下文内**发生（图片层自己有 z-index，所以它自己形成一个组，把混合关在里面）；
- 遮挡层出现之前，图片下面**什么都没有**——背景板透明，按规范混合退化成"不混合"，所以这行声明一直是死代码；
- 遮挡层一出现，图片下面就有了一块近乎中性的底色，`luminosity` 拿它的**亮度**配上背景板的**色度**——中性色度就是灰。于是那一带里的图片全变黑白。

修法是**删掉这个混合模式**，而不是想办法把它挡住：混合模式的语义就是"颜色取决于我下面画了什么"，而"图片的颜色不能取决于底下画了什么"恰恰是分层能成立的前提。测试里现在有一条断言：整张样式表**不允许出现 `mix-blend-mode`**。
#### 更多图片

「添加图片」旁边加了「更多图片」，宽度 2:1，跳到 [ai-meme.cdqyfdbymn.me](https://ai-meme.cdqyfdbymn.me)——一个 DeepSeek 表情包合集。它是**跳转到系统浏览器**，不是内嵌页面：地址是第三方的，本插件不为上面的内容背书，而且一张图值得先看一眼再决定要不要当背景。走 `window.open(..., 'noopener,noreferrer')`，和充值页的浏览器回退同一条路径（顺手抽成了 `openExternal`），不做成 `<a href>`：这些浮层 portal 在应用路由之外，裸链接会被壳内的处理器接走而不是浏览器。

### 4. 界面配色自定义（第四层 token）

「背景」入口打开的面板现在是**两栏**：左边是背景图片（第 3 节），右边是配色。做成并排而不是分页，是因为这两件事经常要一起调——把底色压暗一点，往往紧接着就要把文字提亮一点——而分页会把另一栏藏起来。两栏各自滚动，所以图片列表再长也压不掉下面的颜色旋钮。

右栏 22 个旋钮，每个**只对应一个 token**：

| 组 | 旋钮 → token |
|---|---|
| 整体与表面 | 整体底色 `alias-bg-base` · 面板与浮层 `alias-bg-layer-2` · 控件与标签底 `alias-bg-module-platform` · 弹出层材质 `menu-surface-fill` · 左侧边栏 `specific-sidebar-fill` · 会话气泡 `specific-bubble` |
| 文字 | 主要文字 `alias-label-primary` · 次级文字 `alias-label-secondary` · 弱化文字 `alias-label-tertiary` |
| 强调与按钮 | 强调色 `alias-brand-primary` · 主要按钮 `alias-button-primary-fill` · 链接与操作 `alias-link` · 悬停底色 `alias-interactive-bg-hover` |
| 线条与代码 | 边框与分隔线 `alias-border-l2` · 代码块底 `alias-markdown-code-block` |
| 状态色 | 成功 `state-success-primary` · 警告 `state-warn-primary` · 错误 `state-error-primary` |
| 角落按钮（本插件） | 按钮底色 `--dsd-chip-fill` · 按钮描边 `--dsd-chip-stroke` · 按钮文字 `--dsd-chip-ink` · 余额数字 `--dsd-chip-ink-strong` |

**这些名字是量出来的，不是想出来的。** 第一版按官方设计系统对 token 的*意图*命名，那是另一个问题：`--dsw-alias-bg-module-platform` 上游描述是"模块表面"，但实际用它的是选择器、标签和设置卡片，而屏幕上唯一明显变化的东西是本插件自己的余额芯片——于是"输入框与模块"这个名字读起来就像在骗人。现在每个旋钮的 tooltip 都带一份实测证据：

```
整体底色
--dsw-alias-bg-base
实测改动 83 处 / 17 个包
选择器：.frame · .inspectButton · .bannerWrap · .image
```

这份数据由 `analysis/embed-consumers.mjs` 从**已安装应用**的样式表里扫出来，写进 `client.js` 的 `@dsd-consumers` 生成区块。它也是那些改名的依据：`别名 品牌色 → 强调色`、`悬浮高亮 → 悬停底色`、`主按钮 → 主要按钮`、`分隔线 → 边框与分隔线`、`代码块 → 代码块底`、`链接 → 链接与操作`、`菜单与弹窗 → 弹出层材质`、`卡片与浮层 → 面板与浮层`。

**"是否列全了"这个问题的答案，面板自己会写出来**：底部一行给出分子和分母——`本栏 22 项。官方可调 token 共 120 个（alias 107 · specific 11 · menu 2）；另有 51 个包直接写死了颜色，任何 token 都改不到。` 分子来自旋钮表，分母是扫出来的（和 [THEME-SURFACE.md](THEME-SURFACE.md) 用同一条规则统计，所以两处不会互相矛盾）。只给分子的话，会让人以为已经覆盖全部。

**本插件自己的部件用自己命名的 token。** 两个角落按钮（余额、背景）是这个插件画的，不是应用画的。让它们去读 `--dsw-*` 有双重的错：一是"输入框与模块"这个旋钮会顺手重绘余额芯片（它最显眼的受害者，也是那个名字读起来像谎话的原因），二是**背景按钮根本没法上色**——它原本是透明的，压根没有属于自己的表面。现在它们读 `--dsd-chip-*`：`overrideTokens` 不关心 token 叫什么（呈现器会把合成快照的每一项都写到 `body` 上），所以插件可以给自己的部件拥有变量、把它们做成旋钮，而不是借应用的名字。

几个不那么显然的设计决定：

- **一个旋钮是两个值，一浅一深**。这不是我加的复杂度，是官方 `overrideTokens` 的硬要求：它只接受 `{ light, dark }`，**给字符串会直接抛一段教学式错误**——"a single value goes illegible when the user switches color scheme"。一个颜色确实没法同时伺候白底和近黑底。
- **右栏有两个开关，它们不是一回事。** 上面那个「应用配色」是**真的切换应用**（跟随系统／浅色／深色），走的是主题服务唯一的偏好写入口 `setTheme()`，和「设置 → 外观」写的是同一个值——所以两处不可能不一致。下面那个「正在编辑哪一套值」只决定下面的旋钮改哪一份数据，不动应用。
  第一版只有一个"浅色/深色"开关，本意是后者，但看起来像前者，于是"点了没反应"。现在切换应用配色时会把"编辑哪一套"重置为跟随，避免出现"看着深色界面却在改浅色值"。
- **主题变化是订阅来的，不是猜的。** 插件用 `ctx.on('theme/change', …)` 把主题服务的状态镜像进 store，因此不管配色是从哪边翻的——设置面板、本插件、还是 `跟随系统` 下的系统切换——面板都会重绘，色块也会重新读取。同一份 revision 也是实时颜色缓存的键：拖图片时它不变，所以那一帧不会重读 22 次计算样式。
- **没动过的旋钮，一个 token 都不写**。层里只出现你碰过的那些，其余保持原样——包括第三方皮肤设的值。这就是"未触碰 = 不写"，也是为什么这些旋钮的存储是稀疏的、而不是开机就把 22 个值全填一遍。
- **调色盘会保留透明度**。原生 `<input type="color">` 根本没有 alpha 通道，而这里有几个旋钮本身就是淡色（悬停底色 `#1d4ed80f` 只有 6% 不透明）或发丝线（边框与分隔线 `#1d4ed824`）。如果换色时把 alpha 丢掉，一条发丝线会在你调色相的瞬间变成实心块。所以文本输入框接受 6 位和 8 位十六进制，调色盘只负责改动 RGB，alpha 从原值带过来。
- **显示的值优先从页面上读**。`body` 的行内自定义属性是布局呈现器的产物，所有覆盖层（本插件的、别的皮肤的）都会以字面颜色出现在那里；读不到再退到 `getComputedStyle`（原厂色板在那儿，`var()` 链也已经代入）；再读不到才用插件记录的表。所以装了别的皮肤时，色块显示的仍然是**你实际看到的颜色**，而不是插件以为的颜色。表里的 44 个值也不是抄的：`analysis/palette-defaults.mjs` 把它们和**已安装应用**里的实际取值逐条比对。
- **输入中的半成品不会落盘**。只有解析成完整十六进制时才提交——所以敲到一半的 `#41` 不会被当成颜色、也不会把原来的值清掉；它只存在于输入框的草稿里，失焦就丢。校验失败的字符串永远到不了主题层。
- **预设是那七套。** 每一套写的都是**六个颜色**（亮/暗各三个锚点：画布、墨色、强调色），其余 16 个旋钮值由 `presetPalette()` 推导：
  - 「DeepSeek 品牌蓝」——品牌梯级（500 `#4176e6`、450 `#5686fe`、400 `#7aaaff`、100 `#e4edfd`）。它**刻意比自带皮肤更重**：自带皮肤已经把底色、文字和按钮染成品牌色了，一个只是复述这些值的预设点下去会像什么都没发生；这个预设还接管了**侧边栏、会话气泡和代码块**——也就是自带皮肤不碰的地方。
  - 「护眼绿」——表面是偏暖、几乎不带绿的纸感色（高饱和的绿底恰恰是最不护眼的），墨色是偏绿的近黑而不是纯黑（对比度够高，又没有纯黑压白那么硬），强调色（同时驱动本插件的滑杆和选中框）是一片哑光叶绿。**状态色故意不动**——成功本来就是绿的，再把它染一遍会让"成功"和"选中"变成同一个颜色。
  - 「暖阳琥珀」米色纸面 + 琥珀强调；「紫罗兰」淡紫、偏冷偏安静；「青瓷」冷调青绿，比护眼绿清爽；「墨玉黑」几乎没有色相，暗色是真黑（OLED 省电）；「高对比」纯黑白底 + 饱和强调色 + 明显边框，为可读性做的。
  - **手写 19 个值 × 7 套 = 133 次打错一个数字的机会**，而每一个都只会在界面某个角落里显形。所以锚点才是手写的，其余全是算术：表面 = 向墨色或强调色混合，文字两档 = 墨色按 62% / 42% 混向画布，悬停与描边 = 强调色加 alpha。亮色列里墨色是深的，混合就是变深；暗色列里墨色是浅的，同一个表达式就是变浅——所以一套方案只需要一份规则。
  - **有一条会失败的测试守着它**：7 套 × 2 个模式，用 WCAG 相对亮度算正文对画布的对比度（≥7:1）、次级文字（≥3.5:1）、弱化文字（≥2.2:1），再校验"亮色方案必须是亮底深字"（防止生成出来的配色把某一列弄反），以及每套的强调色不与别套重复。也就是说这七套是**算过**能读的，不是"我觉得好看"。
  - 预设写完之后仍然是普通的旋钮状态，可以接着单个改；「恢复默认」清空的正是这一层。
- **那 30 多个没有旋钮的别名，是常驻的。** 应用一共 405 个可调 token，旋钮只覆盖 22 个。剩下那些——其他层级描边、悬停/按下底色、悬浮按钮底、插件市场的勾选色 `--dsw-alias-brand-primary-new-colorprimary-new-color`、代码块家族、滚动条、文档选中色、两个"深度思考"标签色——原来一直留着自带皮肤的**藏青**。蓝色方案里看不出来，换成琥珀或墨玉黑，每一处都是一块蓝色鬼影（这正是用户报回来的：内联代码、`present` 出来的文件卡、回到最底部按钮、新会话按钮、设置左侧项目的悬停底色）。
  修法不是逐个去猜，而是**先审计**：把应用定义的全部别名解析一遍（`var()` 链展开到 `--dsw-static-*` 或字面量），按色相和饱和度筛出偏蓝的那些，再减去插件已经写过的——剩下 8 个，其中 3 个是真的蓝（文档选中色、两个 deep-diving 标签），另外 5 个只是带一点蓝味的灰（`#ebeef2` 这种），不值得动。
  这 30 多个值写成一张 `DERIVED_TOKENS` 表，**放在常驻的品牌层**里，而不是只跟着预设走。关键在它们的写法：全部是 `color-mix()` 套在**旋钮会设的那些 token** 上（`var(--dsw-alias-brand-primary)` 之类），所以它们跟随的是**当前生效的强调色**——改旋钮也好、点预设也好，整块界面（包括那些没有旋钮的角落）同时跟着走。这也是为什么表里给浅色和深色写的是同一个字符串：它读的那些 token 本身就是分模式的。
  **这条规则是把这件事做对的关键，而我第一次没守住它。** 表里最初有 6 处写成 `var(--dsw-alias-bg-layer-3)` —— 一个**没有旋钮、预设也不写**的表面 token。于是它解析出来仍然是自带皮肤的值（浅蓝），代码块标题、内联代码、悬浮按钮 hover 在暖色方案下照样是蓝的。用户回来说"没变化"就是这个原因。
  正确的判据不是"这个 token 存不存在"，而是**"这个 token 的值会不会跟着用户的选择走"**。所以判据写成了：一个颜色只有在**被旋钮覆盖**（在 `COLOR_SLOTS` 里）或**被推导**（在 `DERIVED_TOKENS` 里，且只引用上面那些）时才算"跟随"。按这个判据再审一遍，还揪出**插件自己品牌层里的 8 个**：`brand-text`、`button-primary-hover`、`button-primary-dimmed`、`button-info-fill`、`button-info-hover`、`label-primary-dimmed`、`label-caption`、`brand-primary-invert`——它们的出厂值是字面品牌蓝，而且恰好都没有旋钮，所以暖色方案下信息按钮和它的 hover 一直是蓝的。这 8 个现在也推导了，`frozen blues` 归零。
  这条判据做成了 `analysis/blue-audit.mjs`（可当闸门：有冻结色就非零退出），并且**接进了 `plugin-guards.mjs`**——同一个错误在这个项目里犯过三次（应用的别名、预设的载荷、插件的品牌层），所以它现在是被检查的，不是被记住的。
  **最后一处蓝色在两个 `--dsw-specific-*` 变量上。** 设置面板左侧栏目的选中/悬停底色不是别名 token，而是 `--dsw-specific-sidebar-nav-item-active` / `-hover`——应用在自己的样式表里用写死的藏青色声明它们，没有任何旋钮、也没有任何层写过它们，所以任何方案下它们都是蓝的。它们和别名一样声明在 `body` 上，所以行内层照样赢；现在也推导了（强调色按 20% / 10% 混进面板底色）。**注意这里越出了 `--dsw-alias-*` 的惯例**：值仍然是"跟随锚点"的，只是名字属于另一族。
- **它在第四层，永远赢过自带皮肤**。`overrideTokens` 按注册顺序叠，后注册的赢；这一层在自带皮肤和本插件 chrome 层之后注册，所以用户的选择不会被它们盖掉。它在 `apply` 里注册，并把返回的 disposer 存起来，**卸载/关闭插件时会把这一层收回去**——否则关掉插件会留下一套没人能再撤销的颜色，因为写它的面板已经跟着走了。
- **推送要先去重**。`overrideTokens` 是整个 source 的层替换，所以"实时预览"就是重新推一次；但它同时会 `publish` 一个新的主题快照，而布局呈现器收到 publish 会把**每一个 token 重写到 `body` 上**。店里每次变化都推一次的话，拖动一张图片的每一帧都会重写几百个行内属性。所以桥里先比对该层的 JSON，一样就不推。
- **颜色和图片分开存、分开写**。颜色在 `dsd:colors:v1`，图片在 `dsd:background:v2`；图片那份是几 MB 的量级，调个色相没道理重写一遍照片列表，所以两个写入器各自独立防抖。写图片那份时会**显式剔除 `colors` 字段**，让 `dsd:background:v2` 始终是纯图片负载。

这一轮的三个 bug 都是新测试先抓到的，值得记下来：

1. **图片读取器把颜色负载整个吃掉了**。`readStoredJson` 校验的是图片形状（必须有 `items` 数组），拿它去读颜色 key 会**静默返回 `null`**，于是每次启动都把已保存的颜色丢光。修法是加一个只校验"是对象"的兄弟函数 `readStoredObject`，而不是给前者加开关——形状校验对图片那一侧是有价值的，只是不该兼职。
2. **开机那次推送推错了东西**。`push` 接受的是整个 state、从里面取 `.colors`，而 `apply` 里传的是已经取好的 `.colors`，于是 `state.colors` 恒为 `undefined`、负载恒为空。症状很隐蔽：**保存的颜色在重启后不生效，直到你随便动一下界面触发下一次 store 变化才突然出现**。日志里"2 of 18 knobs overridden"和实际注册的层是空的对不上，这就是线索。
3. **颜色跟着图片一起写进了图片 key**。`flushSave` 原本序列化整个 durable 对象，现在显式删掉 `colors`。

### 5. 角落常驻余额显示

**不需要 API key。** 通过宿主已经暴露的账号 Remote 读取，和「设置 → 账户」显示的是同一个数：

**刷新节奏：每 15 分钟一次**（`apply` 里的 `refreshMinutes = 15`），另外**点一下立即刷新**。不是 60 秒。这个节奏没有设置项，所以它被写进了芯片自己的 tooltip：`账户余额 ¥x · 每 15 分钟自动刷新 · 单击立即刷新 · 双击充值`——一个常驻角落的数字，用户第一个问题就是"它自己会更新吗"，而这是唯一能回答的地方。

```js
ctx.remote.account.getBalance({ version, locale, timezoneOffsetSeconds })
```

返回值 `{ ok, value: { value: [...wallets], bonusWallets: [...] } }`。

显示规则：

| 状态 | 圆点 | 显示 | 悬浮说明 |
|---|---|---|---|
| 正常 | 绿 | `¥128.40` | 账户余额 + 单击刷新 · 双击充值 |
| 余额为 0 | 琥珀 | `¥0.00` | 余额不足，双击充值 |
| 读取中 / 刷新中 | 灰 | `…` | 正在读取 |
| 未登录账号 | 灰 | `—` | 未登录账号，无法读取 |
| 读取失败 | 红 | `—` | 读取失败 · 点击重试 |

「余额为 0」和「读取失败」显示不同的颜色与文案——这两种情况对用户意义完全不同，不能都显示成一道横线。

金额格式对齐 Platform Web：两位小数、千分位分组、正的次分级金额显示 `<¥0.01`。多钱包按币种累加（充值 + 赠送），优先显示 CNY。

**位置**：注册在 `sidebar.footer.action`——侧栏底部固定的 seat 区，与设置按钮并排，不点击即可看到；侧栏折叠时同一个数在 `sidebar.toggle.badge` 以极小字号保留。

刷新间隔 15 分钟，点一下芯片也会立即刷新。

#### 单击刷新 / 双击充值 怎么区分

浏览器把双击送成**两个 `click` 事件**（外加一个 `dblclick`），所以不能简单地各挂一个处理器——那样双击会先刷新两次再跳转。做法是**等一拍**：

```js
onClick: () => {
  if (timer) { clearTimeout(timer); openTopUp(); }        // 第二击：跳转
  else timer = setTimeout(() => { timer = null; refresh(); }, 260);  // 第一击：等 260ms
}
```

260ms 内没有第二击才刷新——短到单click 感觉不出延迟，又长到足以吃掉一次双击。定时器在卸载时被清掉，不会留下一个比组件活得久的回调。

**跳转目标**与官方「充值」按钮一致：桌面版不导航，而是请 `globalThis.dshPlatform`（Electron 宿主注入的全局）在**宿主自己的 `WebContentsView` 里**显示 Platform 充值页。协议照抄官方 `ui-settings-account`：

```js
dshPlatform.open('top-up', bounds)   // bounds = 视口矩形的 x/y/width/height
dshPlatform.setBounds(bounds)        // 窗口尺寸变化时同步
dshPlatform.close()                  // 卸载时释放
```

三点刻意的设计：

- **原生页面上方永远留着一条自己的 chrome（「‹ 返回」+ Escape）**。原生 view 画在文档**之上**，如果只调 `open()` 而不给退路，页面一旦开出来就没法关掉——这是这里唯一会造成"卡住"的失败模式，所以退路必须先存在。
- 视口矩形从 `<div class="dsd-topup-viewport">` 实测得到，并用 `ResizeObserver` 跟随；矩形没测到时（比如非浏览器环境渲染）**不会**去 claim 原生 view，而是留在状态页。
- 没有 `dshPlatform` 的宿主（纯 Web 版）自动退回 `window.open('https://platform.deepseek.com/top_up')`。这条退路官方 `ui-settings-account` 联系表单也在用。

#### 按钮布局是抄官方的，不是自己设计的

第一版这条 chrome 是**自己写的**，结果左上角的「返回」和窗口标题栏那几个按钮（收起侧边栏 / 应用 / 编辑）**叠在一起，两边都点不动**。查了官方 `ui-settings-account` 的 `PlatformOverlay` 才明白差在哪——它多了两件事：

```css
.overlay { position: fixed; inset: 0; z-index: 1001 }
[data-windows-titlebar] .overlay { padding-top: var(--dsh-windows-titlebar-height) }
.header  { height: 48px; padding: 6px 16px; border-bottom: .5px solid var(--dsw-alias-border-l1);
           -webkit-app-region: initial }
```

- **`padding-top: var(--dsh-windows-titlebar-height)`**：Windows 上标题栏是应用自己的 DOM（`.frame:before` 画那条拖拽带），高度由这个变量公布。不把它让出来，任何全屏浮层都会盖到那几个按钮上。
- **`z-index: 1001` + portal 到 `document.body`**：帧内最高的一层是 `overlayLayer` 的 `z-index: 20`，在它里面无论怎么调都赢不了标题栏。
- 官方的 48px 行高、`gap: 24px`、macOS 专用 60.667px 红绿灯占位、以及 `-webkit-app-region: initial`（否则这行会变成窗口拖拽区，按钮点不动），全部照搬。

所以现在这个浮层的样式表就是官方那套的等价物，只是类名前缀换成了 `dsd-topup-`。

图层、编辑器、充值页宿主**都注册在 `shell.overlay`**（root 作用域的列表插槽），但内容都 portal 到 `document.body`。两个理由：图片必须在「新会话」页也存在，而 `conversation.composer.dock` 只在会话页渲染；同时帧内的 `overlayLayer` 是 `z-index: 20`，图片放进去会盖住侧栏而不是当背景。关闭时组件返回 `null`，插槽包装元素是 0 尺寸，不挡任何点击。

## 安装（bundle 方式，当前采用）

本插件已注册为 profile 的**一个真实 bundle**，因此会出现在 Plugin Manager 的「Installed」列表里并带开关。落地为三处改动：

**1. profile 的 `package.json`** —— 加一条依赖，并把包名加进 bundles 列表：

```json
{
  "dependencies": {
    "dsh-diy-skin": "link:<本仓库的绝对路径>/dsh-diy-skin"
  },
  "dsh": { "profile": { "bundles": [
    "@deepseek-ai/dsh-base",
    "@deepseek-ai/dsh-web-app",
    "dsh-diy-skin"
  ] } }
}
```

**2. 在 profile 目录跑一次 `pnpm install`** —— 解析 `link:` 依赖。

**3. profile 的 `cordis.patch.yml`** —— 移除早先手写的那条 `insert`；插件行现在由 **bundle 自己的 patch**（`package.json` 的 `dsh.bundle.patch`）提供，用的是**裸包名**：

```yaml
- insert:
    - id: deepseek-decor
      name: 'dsh-diy-skin'
```

这三步等价于官方 `install_bundle` 所做的事，可用 `preview/register-bundle.py` 复现（默认干跑，加 `--apply` 才写）。

### 为什么用 `link:` 而不是 `file:`

实测两者差别：

| 写法 | 能装上 | 工作目录改代码是否立即生效 |
|---|---|---|
| `file:<绝对路径>` | ✅ | ❌ 是**复制**，每次改都要重装 |
| `link:<绝对路径>` | ✅ | ✅ 生成 junction，**实时生效** |

因为后续还要反复调样式，选 `link:`——工作目录始终是唯一来源，改完只需刷新页面（若改了宿主半侧或 profile 配置才需要重启）。

另外，`file:` 与 `link:` 都必须用**绝对路径**：相对路径里 `..` 的层数依赖 pnpm 的解析规则，我实测推错过两次，绝对路径没有歧义。

### 早期的写法与它的坑

最初我用「profile 补丁里插一条绝对路径行」的方式安装，踩了一个很隐蔽的坑，值得留着：

DSH 加载器会把 `insert` 里**绝对路径**形式的 `name` 转成 `file://` URL 直接 import（`anchorInsertedPluginNames`，`dsh-app-boot/lib/index.js`），而 **ESM 不允许导入目录**：

```
Error: Directory import '...\dsh-diy-skin' is not supported resolving ES modules
Did you mean to import ".../dsh-diy-skin/index.js"?
```

包里的 `exports["."]` 只在**按包名解析**时生效，对 `file://` 目录 URL 不起作用。写目录的后果是：宿主半侧从未挂载 → 没有 fiber → 不触发 `internal/plugin` 事件 → `client-modules` 的 `dsh.client` 扫描收不到这个包 → 客户端 bundle 从未进入 `__DSH_BOOT__` 的 `entries` → **界面零变化，且控制台没有任何报错**。整条链路静默断在第一环。

改成指向 `index.js` 后能工作，但那只是补丁行方案；bundle 方式用裸包名，走的是标准解析路径，不存在这个问题。

本包**刻意零依赖、且不导出 `Config`**：`Config` 需要 `@deepseek-ai/schemastery`，而它没有随安装目录发布；声明成依赖会让包管理器去 registry 拉一个未必匹配当前构建的版本，而 profile 依赖一旦解析失败，整个 profile 就启动不了。可调项因此写在本文档里，而不是走 `Config`。

## 开关

**插件 → 已安装 → 本插件卡片右侧的开关**（卡片和它的详情页各有一个）。它改的是 `dsh.profile.bundles`：**关掉只是把包名从列表里移除，`dependencies` 里的 `link:` 依赖保留着**，所以再点一下就开回来，不需要重装。

（详情页里还有**行级**开关，那个走 `pluginManager.setPluginEnabled`，往 `cordis.patch.yml` 写 `disabled` 覆盖。只关心整个插件开/关的话用卡片上那个。）

改 `client.js` 源码**必须重启应用**才生效：profile 的 HMR 是开着的，但 base 组合包把它配成 `root: []`——按官方文档，`[]` "仅保留显式注册的配置监听"，也就是**源码模块不在监听范围内**。想让源码改完自动热重载，可以在 profile 补丁里覆盖这一条：

```yaml
- id: hmr
  config:
    root: ["."]
```

## 卸载

在 Plugin Manager 里卸载，或手工做三件事：从 profile 的 `package.json` 移除该依赖与 bundles 条目、在该目录跑一次 `pnpm install`、删掉可能残留的 `disabled` 覆盖。调色板层、材质层、样式表、插槽注册都是随插件生命周期释放的 effect，界面随即回到原始配色。

`localStorage` 里的背景图（key `dsd:background:v2`）**不会**被卸载清掉——这是刻意的，误关插件不该弄丢你自己的图。要彻底清干净就在浏览器控制台里 `localStorage.removeItem('dsd:background:v2')`。

## 已知限制

只列你会遇到的事；每一条的来龙去脉在 [DESIGN.md](DESIGN.md)。

- **图片在应用底下**（`z-index:-1`），所以它只出现在应用自己留空的地方。卡片和输入框保留各自的不透明底色 —— 想让它们也透出来，把「面板与浮层」那个旋钮设成带透明度的值。
- **自己加的图会被压到长边 1600px 的 webp**，超大图细节有损；**动图（GIF）例外**，原样保存，所以可能明显更大。
- **动图不能去白底**：那个开关对 GIF 是禁用的（去白底跑在 canvas 上，只有一帧）。
- **没有输入框能精确设定大小和坐标**：拖动、滚轮、四角拉伸，就这些。
- **深色模式下，浅色底图去白底后可能留一点边**：半透明像素和深色背景混色导致的，不是算法能完全消除的。
- **只在 Windows + 已安装的这个 DSH 版本上验证过**：其他平台的标题栏修正不生效（是空操作），也未验证那边有没有同样的问题。
- **图片存在浏览器级 localStorage 里**：同一台机器的桌面应用内持久，换浏览器就没了；卸载插件不会删掉你的图。
- **编辑期间侧栏按钮点不到**（整块界面被隔离罩挡住），退出用面板的 ✕ 或 Esc。
- **弹出层材质被改成不透明**，官方菜单不再是毛玻璃；不喜欢就删掉 `MATERIAL_TOKENS` 那一层。
- **表情包图片自带文字气泡**，当背景会带上那行字；压低透明度或删掉那个条目。
