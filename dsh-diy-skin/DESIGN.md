# 设计记录

这份文件是给想改这个插件的人（包括未来的我）看的：每个决定为什么这么做、试错过什么、哪些数字是量出来的。

用户要看的安装与使用在 [README.md](README.md)；每个颜色旋钮对应界面上哪一处，在 [KNOB-REACH.md](KNOB-REACH.md)；应用自身的可调 token 全景在 [THEME-SURFACE.md](THEME-SURFACE.md)。

## 功能细节与取舍

1. **品牌配色** —— 一层可移除的 alias-token 覆盖层。
2. **弹出层不透明** —— 官方菜单默认是半透明毛玻璃，压在本插件的背景图上会看不清字。
3. **背景图片** —— 一张张**条目**：内置三张也是条目，全部可编辑、可删；也能自己加图，还能加一张**整图壁纸**（"添加壁纸"：铺满窗口、垫在所有图片下面、只保留一张，**也算在 8 张上限之内**）。**图片衬在整个界面所有文字之下**，所以调多不透明都不会盖住字（输入框那一条是唯一例外，见第 3 节的层序图）。左下角「背景」入口进编辑态后，**拖动移动、滚轮缩放、拖四角拉伸（对角固定、长宽比锁定）**；**右键任意一张图片**会在它旁边弹出这张图自己的控制（透明度、模糊、去白底及其参数）——只有这些，因为大小和位置是手的事。面板里同样只剩「手说不出来」的那些，另有两条「全部图片」批量滑杆；面板可拖动，底部显示占用与余量。编辑期间有一层透明隔离罩，不会误选中会话里的文字。
4. **界面配色自定义** —— 同一个面板的右栏，22 个旋钮，每个对应界面上一处（底色 / 侧栏 / 气泡 / 文字 / 按钮 / 链接 / 分隔线 / 代码块 / 状态色 / 两个角落按钮…）。十六进制输入 + 系统调色盘，浅色/深色分开编辑，「应用配色」可直接切换浅色/深色/跟随系统，自带 **7 套预设**（DeepSeek 品牌蓝 / 护眼绿 / 暖阳琥珀 / 紫罗兰 / 青瓷 / 墨玉黑 / 高对比）。鼠标停在旋钮名字上会说**这个颜色在哪里看得到**；那份实测依据在 [KNOB-REACH.md](KNOB-REACH.md)。除了这 22 个旋钮，插件还**常驻**接管了另外 30 多个应用别名（其他层级描边、各种悬停底色、悬浮按钮底、插件市场的勾选色、代码块家族、滚动条、文档选中色）——它们全部写成"跟随上面那些旋钮"的 `color-mix()`，所以改任何一个旋钮，整个界面（包括那些没有旋钮的角落）都会跟着走，不会留下蓝色鬼影。**除了那 7 套预设，你还可以把自己的调色板存成一套命名的方案**：「存为方案」把当前屏幕上整套 22 个旋钮的值存下来（不是"改过的那几个"的差量，所以回来时一模一样），方案排在预设后面，点一下应用；删除要点两次（第一次变成「确认删除」，旁边有「取消」），因为方案是你亲手起的名字，没有文件可以重新导入。
5. **去白底** —— 每张图一个勾选框。勾上之后用**从四边向内漫水填充**去掉白色背景（主体**内部**的白色会保留），两个旋钮**即时重算、即时预览**：**容差**（多白算背景）与**收边 / 扩边**（±3px，修白边或修被啃掉的地方）。**改哪个旋钮就存哪个旋钮**——参数记在图片上，下次打开还是你调好的样子；**取消勾选就回到原图**（连削掉的那份副本一起释放）。没有"确认"这一步：你要保留的本来就是你自己的照片，不该由一次点击来决定它还在不在。
6. **动图（GIF）** —— 可以直接当背景或贴纸：**原样保存，不缩放、不重编码**，所以动画保留。代价写在明处：动图的"去白底"开关是**禁用**的（去白底跑在 canvas 上，而 canvas 只有一帧，硬做会把动图变成静图）。一张 1600px 的静图约 0.15 MB，动图通常更大——读数条上能看到实际占用。
7. **角落余额** —— 常驻显示，单击刷新，**双击跳转充值页**。

配色到底能改哪些地方，见 [THEME-SURFACE.md](THEME-SURFACE.md)（那份清单由脚本从已安装的应用里读出来，不是凭印象写的）。

### 1. DeepSeek 品牌配色（主题层）

以一层可移除的 alias-token 覆盖层压在当前主题之上，通过官方扩展点
`ctx.theme.overrideTokens()` 注册，因此：

- 基础主题（light / dark / system）保持原样，只覆盖被点名的 token；
- 插件卸载时这一层被整体移除，自动还原成原色板；
- 亮色值 / 暗色值成对提供（这是该 API 的硬性要求，单值会导致切换配色后读不清）。

关键改动不是「加点蓝」，而是**从语义源头接管品牌色**。

这一点我第一版做错了：我直接覆盖 `--dsw-alias-button-primary-fill`，却绕过了它的上游。实际的依赖链是

```
--dsw-alias-brand-primary = 近黑 #0f1115（亮）/ 近白 #f9fafb（暗）
  ├── --dsw-alias-button-primary-fill = var(--dsw-alias-brand-primary)
  ├── --dsw-alias-brand-text
  └── （与 --dsw-alias-label-primary 同一族）
```

只改末端 token，整条链的其余部分仍是中性色，加上亮色底本来就是纯白——**结果就是"看不出来"**。现在改为覆盖语义源以及承载视觉面积最大的表面层：

| Token | 原来（亮 / 暗） | 现在（亮 / 暗） |
|---|---|---|
| `--dsw-alias-brand-primary` | 近黑 `#0f1115` / 近白 `#f9fafb` | 品牌蓝 `#4176e6` / `#5686fe` |
| `--dsw-alias-brand-text` | 近黑 / 近白 | `#4176e6` / `#7aaaff` |
| `--dsw-alias-button-primary-fill` | 继承 brand-primary | `#4176e6` / `#7aaaff` |
| `--dsw-alias-button-primary-hover` | 中性深灰 / 浅灰 | `#3a68d4` / `#93bcff` |
| `--dsw-alias-link` | 深蓝 / `#7aaaff` | `#2f62d6` / `#7aaaff`（提对比） |
| `--dsw-alias-bg-base` | 纯白 / 中性灰 `#151517` | 纯白 / **藏青** `#0d1424` |
| `--dsw-alias-bg-layer-2` | 纯白 / `#2c2c2e` | **蓝调** `#f4f8fe` / `#16203a` |
| `--dsw-alias-bg-layer-3` | 纯白 / `#1c2846` | **蓝调** `#eef4fd` / `#1c2846` |
| `--dsw-alias-label-primary` | `#0f1115` / `#f9fafb` | 藏青墨 `#101a33` / `#eef2fb` |
| `--dsw-alias-border-l2` | 中性黑 10% / 白 12% | 蓝调 `#1d4ed824` / `#ffffff20` |

底色仍保持纯白，是为了不牺牲正文对比度；蓝色集中在**表面层次**（layer-1/2/3）和**品牌源**上，这样主题才真的读起来是"蓝色界面"。共覆盖 50 个 token。

暗色模式整体从「中性灰」改成**藏青体系**，和角色形象的深藏青制服同一个色族。

品牌梯级取自 DSH 自带的静态色：`deepseek-500 #4176e6`、`400 #7aaaff`、`300 #b7c8fe`、`100 #e4edfd`、`50 #edf3fe`。

### 2. 弹出层改成不透明（第二层 token）

输入框左下角的 **「+」打开的是「命令菜单」**，它由 `ui-input-trigger` 渲染成一个 `MenuSurface`——**正好弹在左下角那张 Q 版背景图上**。而官方菜单材质是刻意做成毛玻璃的：

```css
.material { background: var(--dsw-menu-surface-fill);
            backdrop-filter: var(--dsw-menu-backdrop-filter); }
```

| Token | 官方值（亮 / 暗） |
|---|---|
| `--dsw-menu-surface-fill` | `#f8f9fa94`（**58% 不透明**）/ `#43454a73`（**45%**） |
| `--dsw-menu-backdrop-filter` | `blur(40px) saturate(150%)` |
| `--dsw-specific-menu` | `#f8f9faf0` / `#303136f0`（94%，仅缺蓝调） |

45% 不透明的深灰 + 40px 模糊底下压着一张浅色插画，就是"看不清内容"。修法是把它改成**完全不透明并关掉模糊**：

| Token | 现在（亮 / 暗） |
|---|---|
| `--dsw-menu-surface-fill` | `#fcfdff` / `#1a2540` |
| `--dsw-menu-backdrop-filter` | `none` / `none` |
| `--dsw-specific-menu` | `#fcfdff` / `#1a2540` |
| `--dsw-alias-menu-group-header-fill` | `#f7faff` / `#1f2b47` |

四点说明：

- 用**六位十六进制**（没有 alpha 通道）而不是 `rgba(...)`，这样"不透明"是格式上可断言的，测试里就是这么校验的。
- 这是**独立的第二层**（source = `dsh-diy-skin:material`），和品牌调色板可以分别移除。`overrideTokens` 支持多层叠加，后注册的按 token 覆盖。
- `--dsw-menu-surface-fill` **不是** `--dsw-alias-*` 名字，但一样能被覆盖：`validateOverrides()` 只要求值是 `{light, dark}` 成对字符串，名字以 `--` 开头即可；presenter 把 `active.tokens` 里每一项都写成 `body` 上的内联自定义属性。
- 菜单填充色比 `--dsw-alias-bg-layer-2` 略亮一档，保持"浮在表面之上"的层次感。

### 3. 背景图片（全部可编辑）

图层由一串**条目**组成，没有"内置"与"自加"之分：首次运行时那三张图会被**播种成普通条目**，和后来加的图享受同一套控件，也一样能删。

三张图播种时的初始值（就是原来那套固定几何换算过来的，`size` 是高度占视口百分比，`x`/`y` 是**中心点**位置）：

| 图片 | `x` | `y` | `size` | 原来的位置 |
|---|---|---|---|---|
| 全身立绘 | 90% | 80% | 46vh | 右下角，出血出画 |
| Q 版坐姿 | 27% | 90% | 23vh | 左下角，贴内容区左缘 |
| 表情包 | 80% | 12% | 15vh | 右上角，避开会话标题 |

所有图片都用同一套画法：`<img>` + 径向渐变蒙版（边缘向外淡出，避免生硬的矩形边框）+ `pointer-events: none`（不编辑时不接收点击）。**没有混合模式**——原因见下面"背景被两处系统表面盖住"那一节，这是被一个真实 bug 教出来的。

**图片以 data URI 内嵌在 bundle 里**，不是外部文件：DSH 的 web 服务只暴露插件的 bundle（`/plugins/...`），不会伺服包目录里的任意文件，所以 `<img src="../assets/x.webp">` 必然 404。内嵌同时也免疫 CSP 限制。条目里存的是 `builtin: 'chibi'` 这样的**引用**而不是那份 base64，所以三张图不会在 `localStorage` 里再存一遍。

**不再有任何手绘角色图形**：鲸尾标记与手绘半身像都已移除。

#### 左下角「背景」入口：鼠标直接拖

侧栏底部（余额芯片旁边）的 **「背景」** 按钮（图标是官方那条鱼，不是方块）打开编辑器：

| 操作 | 效果 |
|---|---|
| 拖动图片本身 | 移动。图片跟着指针走，**不会**跳到指针中心（抓取点被记下来了） |
| 在图片上滚动滚轮 | 缩放，一格 4vh |
| 拖**四个角**的小方块 | 拉伸。**对角固定不动**，长宽比锁定，所以不会变形 |
| 点空白处 | 取消选中（四个角的小方块只长在选中的那张图上） |
| 拖「全部图片」的两个滑杆 | 一次把所有图片的透明度 / 模糊改成同一个值 |
| 拖单张图的滑杆 | 精确微调这一张：大小 / 水平 / 垂直 / 透明度 / 模糊 |
| 拖面板标题栏 | 把面板挪开——它默认停在左下角，正好压着侧栏那一带 |
| 添加图片 | 选本地图片，可多选，最多 16 张（含壁纸） |
| 删除 / 清除全部 | |
| `Esc` 或右上 ✕ | 退出编辑 |

三条运算规则：

- **移动**：按下时记下指针在图片内部的偏移和 `getBoundingClientRect()`，之后每次移动用「指针位置 − 偏移」换算回中心点百分比。不需要知道渲染宽度。
- **缩放**：**对角是锚点**（这正是"四个角"而不是"四边中点"的原因——边上的把手只能改大小，角上的还隐含了"从哪儿长"）。于是中心必须跟着移动半个尺寸变化量。新高度取指针在「锚点→把手」对角线上的**投影**：`(dx·a + dy) / (a² + 1)`，其中 `a` 是宽高比。抓取那一刻这个投影恰好等于当前高度，所以**按下去不会跳**；而且整个计算只用模型里的数字（含 `aspect`），不需要量 DOM，画出来的和拖出来的不可能不一致。
- **长宽比从哪来**：模型只存高度、宽度自动，所以"渲染宽度"本来是不可知的。现在每张图把自己的 `aspect`（`naturalWidth / naturalHeight`）在图片解码完成时**记进条目里**（`onLoad`，值没变则不写），四个角的位置和缩放运算都由它推出来：
  `left: calc(30% + 40vh)` 这种——`%` 是视口宽、`vh` 是视口高，`calc` 会把两者都化成像素。

监听器一律挂在 `window` 而不是元素上——拖快了指针跑出图片也还在拖。

#### 编辑时会加一层透明隔离罩

进入编辑后，图层里会多出一个**全视口的透明罩**（`.dsd-shield`），它盖在整个应用之上、吞掉所有指针事件、并且 `user-select: none`。目的就是你说的那件事：**拖图片时不会误选中会话里的文字**。

四件事必须一起成立，否则罩子要么漏、要么反而把人困住：

1. **罩子 z-index 1，图片在编辑期间抬到 z-index 2** —— 图片必须盖在罩子上面，否则罩子会把拖动也一起吞掉。
2. **整个图层在编辑期间从 `z-index: 0` 抬到 `15`**。这条是踩出来的：会话面板自带正的 z-index，停在 0 的话罩子会**被会话面板盖住**，输入框仍然能点、会话文字仍然能选中——正是这个隔离罩要防的东西。`15` 高于应用内容，但低于官方浮层（`overlayLayer` 是 `20`）和模态（`1000+`），所以编辑期间官方菜单与弹窗仍然正常。
3. **退出方式**：面板右上 ✕，或 `Esc`。`Esc` 由**图层**注册而不是面板——面板是可能渲染失败的那一个（见下一条），图层不是。
4. **编辑期间滚轮不再滚动应用**（在 `window` 上 `preventDefault`，但放过面板自身的滚动）：否则滚轮会去滚一个被罩子挡住、又看不出在动的界面。

同时要知道：**编辑期间那个「背景」按钮也点不动了**。这是"整块应用被隔离"的直接含义，所以它不是开关；退出靠上面那两条路。

#### 一个把面板彻底搞没了的 React 陷阱

第一版这个编辑器上线后，点「背景」的结果是：**什么都没出现，但除了输入框以外全都点不动了，也退不出去**。

原因是一处 React 规则违反。`DecorEditor` 当时长这样：

```js
function DecorEditor() {
  const state = useDecorState();           // 2 个 hook
  if (state.editing !== true) return null; // ← 提前返回
  …
  React.useEffect(() => { … }, []);         // ← 第 3 个 hook 在返回之后
}
```

关闭状态下它只用 2 个 hook，打开状态下要用 3 个。React 明确拒绝这种更新——**"Rendered more hooks than during the previous render"**——渲染抛错、整个占用者子树被卸载，面板永远不出现。

而罩子为什么还在？因为它属于**另一个**组件（图层占用者，先注册、已经提交成功），不受影响。于是正好形成"罩子立起来了、面板没了、除了 z-index 更高的输入框之外全被挡住、`Esc` 也没注册"的僵局。

修法是把编辑会话的全部副作用都挪进**图层**：它整个生命周期都挂载着、没有提前返回，hook 数量在构造上就不可能变。

**更重要的收获是测试台补上了这个盲区。** 原来的假 React 只按索引存取 hook、不管数量变化，所以 22 项测试全绿却漏掉了这个必崩的 bug。现在渲染器会像真 React 一样比较每个组件两次渲染的 hook 数量，一变就抛：

```
hook count changed for DecorEditor: 2 -> 3. React rejects this update;
look for an early return above a hook.
```

我先把这个检查加进去、**跑出上面这行失败**确认诊断无误，再去改代码。这条检查对以后任何"提前返回写在 hook 之前"的改动都有效。

其它实现要点：

- **每张图是独立的盒子**，`<img>` 而不是背景图，因此**只给高度**、宽度按原图比例自动跟；`transform: translate(-50%,-50%)` 让它以中心点定位。
- 拖滑杆与拖图片都**即时生效**：所有组件订阅同一个 store，改完立刻重画，没有确认按钮。
- **「全部图片」的两个滑杆是"批量写入"而不是"倍数"**：拖一次，把值写给当时列表里的每张图，并记住滑杆停在哪儿。之后再单独调某一张，两者不会互相覆盖——因为你给那张图的是一个具体数字，不是相对量。这不只是设计选择，也是唯一能同时满足"统一控制"和"之后单独调整不受影响"的语义。
- 面板位置（拖过之后）和两个全局值都和图片列表存在同一个 key 里，重启后还在。
- 但**写盘是延后 300ms 的**（trailing debounce）：16 张图时整个 JSON 约 4 MB，拖动每秒能触发几十次变化，每帧序列化一次卡顿会非常明显。内存状态始终最新，只有 `localStorage` 写入在等；插件卸载时会把待写的改动立刻刷掉（`ctx.effect` 的清理函数里调 `decorStore.flush()`）。
- 图片**存在 `localStorage`**（key `dsd:background:v2`），和官方插件管理器记住安装源用的是同一个浏览器级存储，因此重启后仍在、且不写 profile。第一版用的 `dsd:background:v1` 会被**合并进来**而不是丢掉：它自己的图保留，内置三张按当时的 `showBuiltin` 决定要不要补回来。
- **选中时会先压缩**：长边超过 1600px 就经 `<canvas>` 重新编码成 webp（质量 0.82）。不这么做，一张手机照片就会把 `localStorage` 配额撑爆——配额失败会被捕获成面板里的一行提示，而不是抛出去打断渲染。
- 所有存储访问都**双重兜底**：拿不到 `localStorage`（不透明源）就退化成"能用但不持久"，配额溢出就提示。

#### 背景被两处系统表面盖住（以及"面板拖不回来"）

图片层是 `z-index: 0`，所以应用里**任何正值 z-index 的东西都画在它上面**。有两处正好如此，都被用户当场发现了。

**一、右上角三个窗口按钮下面那块。** 这块不是 DOM 画的，是 Electron 的 `titleBarOverlay`——原生矩形，永远在页面之上，CSS 碰不到它本身。但它的**颜色有来源**：桌面 preload 自己造了一个探针元素

```js
probe.style.cssText = 'position:fixed;visibility:hidden;pointer-events:none;'
  + 'background-color:var(--dsw-specific-sidebar-fill);color:var(--dsw-alias-label-primary)';
```

读它的 `background-color` / `color`（过一次 canvas 变成 `rgba()`），再通过 `dsh-desktop:windows-appearance` 交给主进程调 `setTitleBarOverlay`。所以只要让探针的底色变透明，那条通道会自己把透明送过去：

```css
span[style*='--dsw-specific-sidebar-fill']{background-color:transparent!important}
```

这里的 `!important` 是**必需的、也刚好够**：探针颜色是**行内样式**，按级联规则，作者样式表里的 `!important` 声明正好压过普通行内声明。preload 还监听 `head` 的子树变化以及 `body` 的 `style` / `data-ds-dark-theme` 属性，所以本插件往 `head` 插样式表的那一刻，它就会重新读取并上报。三个按钮的**符号颜色**来自同一个探针的 `color`（`--dsw-alias-label-primary`），没有改动——也就是说"主要文字"这个旋钮同时决定它们的深浅。

**二、输入框左右两侧那块。** 这条是应用自己的规则：

```css
.root[data-phase=active] .composerSeat{
  z-index:7; position:sticky; bottom:0;
  background:linear-gradient(180deg, color-mix(… 0%, transparent) 0px, var(--dsw-alias-bg-base) 36px);
}
```

`z-index:7` 让它盖在图片上，而那个渐变在 36px 之后变成不透明底色——它的用途是让正文滚到输入框下面时渐渐淡出，代价是把整个座位区（含输入框两侧）的图片都糊住。现在只清掉座位：

```css
[class*='composerSeat']{background:transparent!important}
```

**输入框本身没有动**（那是应用自己的 `.editor` 规则，不透明是对的），所以正文依然读得清。

**但清掉那块盖版会换来另一个问题**：正文滚到底部时，原来被盖版挡住的字就露出来了。而用户随后提出的更高的要求，正好把整个层序逼到了正确的位置上：

> 图片应该衬于界面上所有文字的下方，但保持输入框底下看不到正文却能看到图片。

### 现在的层序

一句话：**图片在最底下，应用画的一切都在它上面；输入框那一条是唯一的例外，由第二份图片补回来。**

```
   图片层  z-index: -1     ← 整个页面最底，应用画的所有东西都在它上面
   ──────────────────────────────────────────────────────────
   应用的文字、卡片、面板、侧栏、输入框……    ← 全都在图片之上
   ──────────────────────────────────────────────────────────
   输入框那一条：
     ① 遮挡层（不透明底色，只盖对话列底部）   z-index: 5    ← 在文字之上，把正文挡住
     ② 图片的第二份，裁到这一条               同一层，在 ① 之上   ← 于是图片照样看得见
```

**为什么必须画两份。** 图片在最底下就盖不住任何东西——这正是想要的；但"输入框底下看不到正文"要求有个东西**在文字之上**，而那个东西必然也在图片之上，会把图片挡住。一份图片没法同时满足这两件事，所以画两份：一份垫底，一份裁到那一条、盖在遮挡层上。两份走同一个定位函数（同一份 left/top/height/opacity/blur/mask），所以**逐像素重合**，那一条看上去和别处完全一样，区别只是字到这里为止。

**为什么把图片挪到最底下还需要两行额外的 CSS。** 应用有**两块铺满窗口的画布**填着不透明底色：应用外框和中间那一列。图片在它们之下就会被完全盖住，所以这两块必须变透明：

```css
[class*='frame']:has([class*='sidebarCol']){background:transparent!important}
[class*='centerCol']{background:transparent!important}
body{background-color:var(--dsw-alias-bg-base)}
```

两块画布之外还有**第三块**：会话列自己的 root。只把外面两块变透明时，图片会被它挡住，表现是"只有输入框那一条能看到图片"——这正是用户报的那个 bug。它用"里面有没有 composerSeat / composerHero"来认，因为 root 是这套代码里复用最多的类名。用 `:has([class*='sidebarCol'])` 而不是只写 `[class*='frame']`：好几个组件都有以 frame 结尾的类名（附件缩略图就是一个），只有应用外框里面才有侧栏列。这三个名字里**作者写的那一半**（frame、sidebarCol、centerCol）在重新打包后仍然稳定，前面那截哈希不稳定。

最后一行是**把"整体底色"这个旋钮搬到了文档画布上**：那两块画布的颜色本来就是 `--dsw-alias-bg-base`，它们透明之后这个颜色不能丢——它现在画在所有东西的最底下，于是图片边缘被蒙版淡出的地方露出来的仍然是用户选的那个底色。侧栏、卡片、输入框都保留自己的底色，所以"面板浮在壁纸之上"这个观感没有被破坏；想让壁纸也从它们后面透出来，把对应旋钮设成带 alpha 的十六进制值（比如 `#ffffff00`）即可，输入框接受 8 位。

**编辑时会临时反过来。** 图片在应用后面就永远收不到指针事件，也就拖不动。所以进入编辑时整层抬到 `z-index: 15`（在应用所有内容之上、在应用自己的浮层 20 与弹窗 1000+ 之下），由隔离罩负责让应用在这期间不可交互；退出编辑再沉回去。那一条的第二份此时不画，否则它会成为被拖动图片的一个不会动的影子。

顶部那 **44px** 是遮挡层上边缘的渐隐：从全透明到不透明。不然它会是一条横贯窗口的硬边，看起来像一道接缝。那一段之内正文渐渐消失，之外正常显示。

### 试过但不够的两个方案

两个都上线过，也都被用户当场否掉，留下的教训比结论值钱：

- **在座位上做磨砂**（`backdrop-filter: blur(12px)` + 40% 底色）：确实同时做到了"看不到正文"和"看到图片"，但那一层**在图片上面**，所以那一条里的图片又被糊了、又被冲淡了。教训：**任何画在图片这一侧的遮盖物，都会拿走图片的锐度或者强度。**
- **把不透明填充垫在图片下面**（再上一版）：图片保住了锐度，但代价是图片**必须**在应用内容之上，于是不透明度一调到 100% 就把所有文字盖住了。教训：**"文字永远在最上"和"图片永远不被挡"只能二选一——除非分层。**

### 混合模式那一课

遮挡层刚上线时，用户发现图片一进入那一条就**变成黑白**，而带子以外一切正常。原因是 `.dsd-bg` 一直带着 `mix-blend-mode: luminosity`。

它此前什么也没做，现在什么都能做了，因为它终于有了背景板：

- 混合只在**同一个层叠上下文内**发生（图片层自己有 z-index，所以它自己形成一个组，把混合关在里面）；
- 遮挡层出现之前，图片下面**什么都没有**——背景板透明，按规范混合退化成"不混合"，所以这行声明一直是死代码；
- 遮挡层一出现，图片下面就有了一块近乎中性的底色，`luminosity` 拿它的**亮度**配上背景板的**色度**——中性色度就是灰。于是那一带里的图片全变黑白。

修法是**删掉这个混合模式**，而不是想办法把它挡住：混合模式的语义就是"颜色取决于我下面画了什么"，而"图片的颜色不能取决于底下画了什么"恰恰是分层能成立的前提。测试里现在有一条断言：整张样式表**不允许出现 `mix-blend-mode`**。
#### 更多图片

「添加图片」旁边加了「更多图片」，宽度 2:1，跳到 [ai-meme.cdqyfdbymn.me](https://ai-meme.cdqyfdbymn.me)——一个 DeepSeek 表情包合集。它是**跳转到系统浏览器**，不是内嵌页面：地址是第三方的，本插件不为上面的内容背书，而且一张图值得先看一眼再决定要不要当背景。走 `window.open(..., 'noopener,noreferrer')`，和充值页的浏览器回退同一条路径（顺手抽成了 `openExternal`），不做成 `<a href>`：这些浮层 portal 在应用路由之外，裸链接会被壳内的处理器接走而不是浏览器。

按钮做成**描边**而不是实心：两个实心按钮并排会读成两个同等重要的选择，而"去找图"是附带动作。

### 4. 界面配色自定义（第四层 token）

「背景」入口打开的面板现在是**两栏**：左边是背景图片（第 3 节），右边是配色。做成并排而不是分页，是因为这两件事经常要一起调——把底色压暗一点，往往紧接着就要把文字提亮一点——而分页会把另一栏藏起来。两栏各自滚动，所以图片列表再长也压不掉下面的颜色旋钮。

右栏 22 个旋钮，每个**只对应一个 token**：

| 组 | 旋钮 → token |
|---|---|
| 整体与表面 | 整体底色 `alias-bg-base` · 面板与浮层 `alias-bg-layer-2` · 控件与标签底 `alias-bg-module-platform` · 弹出层材质 `menu-surface-fill` · 左侧边栏 `specific-sidebar-fill` · 会话气泡 `specific-bubble` |
| 文字 | 主要文字 `alias-label-primary` · 次级文字 `alias-label-secondary` · 弱化文字 `alias-label-tertiary` |
| 强调与按钮 | 强调色 `alias-brand-primary` · 主要按钮 `alias-button-primary-fill` · 链接与操作 `alias-link` · 悬停底色 `alias-interactive-bg-hover` |
| 线条与代码 | 边框与分隔线 `alias-border-l2` · 代码块底 `alias-markdown-code-block` |
| 状态色 | 成功 `state-success-primary` · 警告 `state-warn-primary` · 错误 `state-error-primary` |
| 角落按钮（本插件） | 按钮底色 `--dsd-chip-fill` · 按钮描边 `--dsd-chip-stroke` · 按钮文字 `--dsd-chip-ink` · 余额数字 `--dsd-chip-ink-strong` |

**这些名字是量出来的，不是想出来的。** 第一版按官方设计系统对 token 的*意图*命名，那是另一个问题：`--dsw-alias-bg-module-platform` 上游描述是"模块表面"，但实际用它的是选择器、标签和设置卡片，而屏幕上唯一明显变化的东西是本插件自己的余额芯片——于是"输入框与模块"这个名字读起来就像在骗人。现在每个旋钮的 tooltip 都带一份实测证据：

```
整体底色
--dsw-alias-bg-base
实测改动 83 处 / 17 个包
选择器：.frame · .inspectButton · .bannerWrap · .image
```

这份数据由 `analysis/embed-consumers.mjs` 从**已安装应用**的样式表里扫出来，写进 `client.js` 的 `@dsd-consumers` 生成区块。它也是那些改名的依据：`别名 品牌色 → 强调色`、`悬浮高亮 → 悬停底色`、`主按钮 → 主要按钮`、`分隔线 → 边框与分隔线`、`代码块 → 代码块底`、`链接 → 链接与操作`、`菜单与弹窗 → 弹出层材质`、`卡片与浮层 → 面板与浮层`。

**"是否列全了"这个问题的答案，面板自己会写出来**：底部一行给出分子和分母——`本栏 22 项。官方可调 token 共 120 个（alias 107 · specific 11 · menu 2）；另有 51 个包直接写死了颜色，任何 token 都改不到。` 分子来自旋钮表，分母是扫出来的（和 [THEME-SURFACE.md](THEME-SURFACE.md) 用同一条规则统计，所以两处不会互相矛盾）。只给分子的话，会让人以为已经覆盖全部。

**本插件自己的部件用自己命名的 token。** 两个角落按钮（余额、背景）是这个插件画的，不是应用画的。让它们去读 `--dsw-*` 有双重的错：一是"输入框与模块"这个旋钮会顺手重绘余额芯片（它最显眼的受害者，也是那个名字读起来像谎话的原因），二是**背景按钮根本没法上色**——它原本是透明的，压根没有属于自己的表面。现在它们读 `--dsd-chip-*`：`overrideTokens` 不关心 token 叫什么（呈现器会把合成快照的每一项都写到 `body` 上），所以插件可以给自己的部件拥有变量、把它们做成旋钮，而不是借应用的名字。

几个不那么显然的设计决定：

- **一个旋钮是两个值，一浅一深**。这不是我加的复杂度，是官方 `overrideTokens` 的硬要求：它只接受 `{ light, dark }`，**给字符串会直接抛一段教学式错误**——"a single value goes illegible when the user switches color scheme"。一个颜色确实没法同时伺候白底和近黑底。
- **右栏有两个开关，它们不是一回事。** 上面那个「应用配色」是**真的切换应用**（跟随系统／浅色／深色），走的是主题服务唯一的偏好写入口 `setTheme()`，和「设置 → 外观」写的是同一个值——所以两处不可能不一致。下面那个「正在编辑哪一套值」只决定下面的旋钮改哪一份数据，不动应用。
  第一版只有一个"浅色/深色"开关，本意是后者，但看起来像前者，于是"点了没反应"。现在切换应用配色时会把"编辑哪一套"重置为跟随，避免出现"看着深色界面却在改浅色值"。
- **主题变化是订阅来的，不是猜的。** 插件用 `ctx.on('theme/change', …)` 把主题服务的状态镜像进 store，因此不管配色是从哪边翻的——设置面板、本插件、还是 `跟随系统` 下的系统切换——面板都会重绘，色块也会重新读取。同一份 revision 也是实时颜色缓存的键：拖图片时它不变，所以那一帧不会重读 22 次计算样式。
- **没动过的旋钮，一个 token 都不写**。层里只出现你碰过的那些，其余保持原样——包括第三方皮肤设的值。这就是"未触碰 = 不写"，也是为什么这些旋钮的存储是稀疏的、而不是开机就把 22 个值全填一遍。
- **调色盘会保留透明度**。原生 `<input type="color">` 根本没有 alpha 通道，而这里有几个旋钮本身就是淡色（悬停底色 `#1d4ed80f` 只有 6% 不透明）或发丝线（边框与分隔线 `#1d4ed824`）。如果换色时把 alpha 丢掉，一条发丝线会在你调色相的瞬间变成实心块。所以文本输入框接受 6 位和 8 位十六进制，调色盘只负责改动 RGB，alpha 从原值带过来。
- **显示的值优先从页面上读**。`body` 的行内自定义属性是布局呈现器的产物，所有覆盖层（本插件的、别的皮肤的）都会以字面颜色出现在那里；读不到再退到 `getComputedStyle`（原厂色板在那儿，`var()` 链也已经代入）；再读不到才用插件记录的表。所以装了别的皮肤时，色块显示的仍然是**你实际看到的颜色**，而不是插件以为的颜色。表里的 44 个值也不是抄的：`analysis/palette-defaults.mjs` 把它们和**已安装应用**里的实际取值逐条比对。
- **输入中的半成品不会落盘**。只有解析成完整十六进制时才提交——所以敲到一半的 `#41` 不会被当成颜色、也不会把原来的值清掉；它只存在于输入框的草稿里，失焦就丢。校验失败的字符串永远到不了主题层。
- **预设是那七套。** 每一套写的都是**六个颜色**（亮/暗各三个锚点：画布、墨色、强调色），其余 16 个旋钮值由 `presetPalette()` 推导：
  - 「DeepSeek 品牌蓝」——品牌梯级（500 `#4176e6`、450 `#5686fe`、400 `#7aaaff`、100 `#e4edfd`）。它**刻意比自带皮肤更重**：自带皮肤已经把底色、文字和按钮染成品牌色了，一个只是复述这些值的预设点下去会像什么都没发生；这个预设还接管了**侧边栏、会话气泡和代码块**——也就是自带皮肤不碰的地方。
  - 「护眼绿」——表面是偏暖、几乎不带绿的纸感色（高饱和的绿底恰恰是最不护眼的），墨色是偏绿的近黑而不是纯黑（对比度够高，又没有纯黑压白那么硬），强调色（同时驱动本插件的滑杆和选中框）是一片哑光叶绿。**状态色故意不动**——成功本来就是绿的，再把它染一遍会让"成功"和"选中"变成同一个颜色。
  - 「暖阳琥珀」米色纸面 + 琥珀强调；「紫罗兰」淡紫、偏冷偏安静；「青瓷」冷调青绿，比护眼绿清爽；「墨玉黑」几乎没有色相，暗色是真黑（OLED 省电）；「高对比」纯黑白底 + 饱和强调色 + 明显边框，为可读性做的。
  - **手写 19 个值 × 7 套 = 133 次打错一个数字的机会**，而每一个都只会在界面某个角落里显形。所以锚点才是手写的，其余全是算术：表面 = 向墨色或强调色混合，文字两档 = 墨色按 62% / 42% 混向画布，悬停与描边 = 强调色加 alpha。亮色列里墨色是深的，混合就是变深；暗色列里墨色是浅的，同一个表达式就是变浅——所以一套方案只需要一份规则。
  - **有一条会失败的测试守着它**：7 套 × 2 个模式，用 WCAG 相对亮度算正文对画布的对比度（≥7:1）、次级文字（≥3.5:1）、弱化文字（≥2.2:1），再校验"亮色方案必须是亮底深字"（防止生成出来的配色把某一列弄反），以及每套的强调色不与别套重复。也就是说这七套是**算过**能读的，不是"我觉得好看"。
  - 预设写完之后仍然是普通的旋钮状态，可以接着单个改；「恢复默认」清空的正是这一层。
- **那 30 多个没有旋钮的别名，是常驻的。** 应用一共 405 个可调 token，旋钮只覆盖 22 个。剩下那些——其他层级描边、悬停/按下底色、悬浮按钮底、插件市场的勾选色 `--dsw-alias-brand-primary-new-colorprimary-new-color`、代码块家族、滚动条、文档选中色、两个"深度思考"标签色——原来一直留着自带皮肤的**藏青**。蓝色方案里看不出来，换成琥珀或墨玉黑，每一处都是一块蓝色鬼影（这正是用户报回来的：内联代码、`present` 出来的文件卡、回到最底部按钮、新会话按钮、设置左侧项目的悬停底色）。
  修法不是逐个去猜，而是**先审计**：把应用定义的全部别名解析一遍（`var()` 链展开到 `--dsw-static-*` 或字面量），按色相和饱和度筛出偏蓝的那些，再减去插件已经写过的——剩下 8 个，其中 3 个是真的蓝（文档选中色、两个 deep-diving 标签），另外 5 个只是带一点蓝味的灰（`#ebeef2` 这种），不值得动。
  这 30 多个值写成一张 `DERIVED_TOKENS` 表，**放在常驻的品牌层**里，而不是只跟着预设走。关键在它们的写法：全部是 `color-mix()` 套在**旋钮会设的那些 token** 上（`var(--dsw-alias-brand-primary)` 之类），所以它们跟随的是**当前生效的强调色**——改旋钮也好、点预设也好，整块界面（包括那些没有旋钮的角落）同时跟着走。这也是为什么表里给浅色和深色写的是同一个字符串：它读的那些 token 本身就是分模式的。
  **这条规则是把这件事做对的关键，而我第一次没守住它。** 表里最初有 6 处写成 `var(--dsw-alias-bg-layer-3)` —— 一个**没有旋钮、预设也不写**的表面 token。于是它解析出来仍然是自带皮肤的值（浅蓝），代码块标题、内联代码、悬浮按钮 hover 在暖色方案下照样是蓝的。用户回来说"没变化"就是这个原因。
  正确的判据不是"这个 token 存不存在"，而是**"这个 token 的值会不会跟着用户的选择走"**。所以判据写成了：一个颜色只有在**被旋钮覆盖**（在 `COLOR_SLOTS` 里）或**被推导**（在 `DERIVED_TOKENS` 里，且只引用上面那些）时才算"跟随"。按这个判据再审一遍，还揪出**插件自己品牌层里的 8 个**：`brand-text`、`button-primary-hover`、`button-primary-dimmed`、`button-info-fill`、`button-info-hover`、`label-primary-dimmed`、`label-caption`、`brand-primary-invert`——它们的出厂值是字面品牌蓝，而且恰好都没有旋钮，所以暖色方案下信息按钮和它的 hover 一直是蓝的。这 8 个现在也推导了，`frozen blues` 归零。
  这条判据做成了 `analysis/blue-audit.mjs`（可当闸门：有冻结色就非零退出），并且**接进了 `plugin-guards.mjs`**——同一个错误在这个项目里犯过三次（应用的别名、预设的载荷、插件的品牌层），所以它现在是被检查的，不是被记住的。
  **最后一处蓝色在两个 `--dsw-specific-*` 变量上。** 设置面板左侧栏目的选中/悬停底色不是别名 token，而是 `--dsw-specific-sidebar-nav-item-active` / `-hover`——应用在自己的样式表里用写死的藏青色声明它们，没有任何旋钮、也没有任何层写过它们，所以任何方案下它们都是蓝的。它们和别名一样声明在 `body` 上，所以行内层照样赢；现在也推导了（强调色按 20% / 10% 混进面板底色）。**注意这里越出了 `--dsw-alias-*` 的惯例**：值仍然是"跟随锚点"的，只是名字属于另一族。
- **它在第四层，永远赢过自带皮肤**。`overrideTokens` 按注册顺序叠，后注册的赢；这一层在自带皮肤和本插件 chrome 层之后注册，所以用户的选择不会被它们盖掉。它在 `apply` 里注册，并把返回的 disposer 存起来，**卸载/关闭插件时会把这一层收回去**——否则关掉插件会留下一套没人能再撤销的颜色，因为写它的面板已经跟着走了。
- **推送要先去重**。`overrideTokens` 是整个 source 的层替换，所以"实时预览"就是重新推一次；但它同时会 `publish` 一个新的主题快照，而布局呈现器收到 publish 会把**每一个 token 重写到 `body` 上**。店里每次变化都推一次的话，拖动一张图片的每一帧都会重写几百个行内属性。所以桥里先比对该层的 JSON，一样就不推。
- **颜色和图片分开存、分开写**。颜色在 `dsd:colors:v1`，图片在 `dsd:background:v2`；图片那份是几 MB 的量级，调个色相没道理重写一遍照片列表，所以两个写入器各自独立防抖。写图片那份时会**显式剔除 `colors` 字段**，让 `dsd:background:v2` 始终是纯图片负载。

这一轮的三个 bug 都是新测试先抓到的，值得记下来：

1. **图片读取器把颜色负载整个吃掉了**。`readStoredJson` 校验的是图片形状（必须有 `items` 数组），拿它去读颜色 key 会**静默返回 `null`**，于是每次启动都把已保存的颜色丢光。修法是加一个只校验"是对象"的兄弟函数 `readStoredObject`，而不是给前者加开关——形状校验对图片那一侧是有价值的，只是不该兼职。
2. **开机那次推送推错了东西**。`push` 接受的是整个 state、从里面取 `.colors`，而 `apply` 里传的是已经取好的 `.colors`，于是 `state.colors` 恒为 `undefined`、负载恒为空。症状很隐蔽：**保存的颜色在重启后不生效，直到你随便动一下界面触发下一次 store 变化才突然出现**。日志里"2 of 18 knobs overridden"和实际注册的层是空的对不上，这就是线索。
3. **颜色跟着图片一起写进了图片 key**。`flushSave` 原本序列化整个 durable 对象，现在显式删掉 `colors`。

### 5. 角落常驻余额显示

**不需要 API key。** 通过宿主已经暴露的账号 Remote 读取，和「设置 → 账户」显示的是同一个数：

**刷新节奏：每 15 分钟一次**（`apply` 里的 `refreshMinutes = 15`），另外**点一下立即刷新**。不是 60 秒。这个节奏没有设置项，所以它被写进了芯片自己的 tooltip：`账户余额 ¥x · 每 15 分钟自动刷新 · 单击立即刷新 · 双击充值`——一个常驻角落的数字，用户第一个问题就是"它自己会更新吗"，而这是唯一能回答的地方。

```js
ctx.remote.account.getBalance({ version, locale, timezoneOffsetSeconds })
```

返回值 `{ ok, value: { value: [...wallets], bonusWallets: [...] } }`。

显示规则：

| 状态 | 圆点 | 显示 | 悬浮说明 |
|---|---|---|---|
| 正常 | 绿 | `¥128.40` | 账户余额 + 单击刷新 · 双击充值 |
| 余额为 0 | 琥珀 | `¥0.00` | 余额不足，双击充值 |
| 读取中 / 刷新中 | 灰 | `…` | 正在读取 |
| 未登录账号 | 灰 | `—` | 未登录账号，无法读取 |
| 读取失败 | 红 | `—` | 读取失败 · 点击重试 |

「余额为 0」和「读取失败」显示不同的颜色与文案——这两种情况对用户意义完全不同，不能都显示成一道横线。

金额格式对齐 Platform Web：两位小数、千分位分组、正的次分级金额显示 `<¥0.01`。多钱包按币种累加（充值 + 赠送），优先显示 CNY。

**位置**：注册在 `sidebar.footer.action`——侧栏底部固定的 seat 区，与设置按钮并排，不点击即可看到；侧栏折叠时同一个数在 `sidebar.toggle.badge` 以极小字号保留。

刷新间隔 15 分钟，点一下芯片也会立即刷新。

#### 单击刷新 / 双击充值 怎么区分

浏览器把双击送成**两个 `click` 事件**（外加一个 `dblclick`），所以不能简单地各挂一个处理器——那样双击会先刷新两次再跳转。做法是**等一拍**：

```js
onClick: () => {
  if (timer) { clearTimeout(timer); openTopUp(); }        // 第二击：跳转
  else timer = setTimeout(() => { timer = null; refresh(); }, 260);  // 第一击：等 260ms
}
```

260ms 内没有第二击才刷新——短到单click 感觉不出延迟，又长到足以吃掉一次双击。定时器在卸载时被清掉，不会留下一个比组件活得久的回调。

**跳转目标**与官方「充值」按钮一致：桌面版不导航，而是请 `globalThis.dshPlatform`（Electron 宿主注入的全局）在**宿主自己的 `WebContentsView` 里**显示 Platform 充值页。协议照抄官方 `ui-settings-account`：

```js
dshPlatform.open('top-up', bounds)   // bounds = 视口矩形的 x/y/width/height
dshPlatform.setBounds(bounds)        // 窗口尺寸变化时同步
dshPlatform.close()                  // 卸载时释放
```

三点刻意的设计：

- **原生页面上方永远留着一条自己的 chrome（「‹ 返回」+ Escape）**。原生 view 画在文档**之上**，如果只调 `open()` 而不给退路，页面一旦开出来就没法关掉——这是这里唯一会造成"卡住"的失败模式，所以退路必须先存在。
- 视口矩形从 `<div class="dsd-topup-viewport">` 实测得到，并用 `ResizeObserver` 跟随；矩形没测到时（比如非浏览器环境渲染）**不会**去 claim 原生 view，而是留在状态页。
- 没有 `dshPlatform` 的宿主（纯 Web 版）自动退回 `window.open('https://platform.deepseek.com/top_up')`。这条退路官方 `ui-settings-account` 联系表单也在用。

#### 按钮布局是抄官方的，不是自己设计的

第一版这条 chrome 是**自己写的**，结果左上角的「返回」和窗口标题栏那几个按钮（收起侧边栏 / 应用 / 编辑）**叠在一起，两边都点不动**。查了官方 `ui-settings-account` 的 `PlatformOverlay` 才明白差在哪——它多了两件事：

```css
.overlay { position: fixed; inset: 0; z-index: 1001 }
[data-windows-titlebar] .overlay { padding-top: var(--dsh-windows-titlebar-height) }
.header  { height: 48px; padding: 6px 16px; border-bottom: .5px solid var(--dsw-alias-border-l1);
           -webkit-app-region: initial }
```

- **`padding-top: var(--dsh-windows-titlebar-height)`**：Windows 上标题栏是应用自己的 DOM（`.frame:before` 画那条拖拽带），高度由这个变量公布。不把它让出来，任何全屏浮层都会盖到那几个按钮上。
- **`z-index: 1001` + portal 到 `document.body`**：帧内最高的一层是 `overlayLayer` 的 `z-index: 20`，在它里面无论怎么调都赢不了标题栏。
- 官方的 48px 行高、`gap: 24px`、macOS 专用 60.667px 红绿灯占位、以及 `-webkit-app-region: initial`（否则这行会变成窗口拖拽区，按钮点不动），全部照搬。

所以现在这个浮层的样式表就是官方那套的等价物，只是类名前缀换成了 `dsd-topup-`。

图层、编辑器、充值页宿主**都注册在 `shell.overlay`**（root 作用域的列表插槽），但内容都 portal 到 `document.body`。两个理由：图片必须在「新会话」页也存在，而 `conversation.composer.dock` 只在会话页渲染；同时帧内的 `overlayLayer` 是 `z-index: 20`，图片放进去会盖住侧栏而不是当背景。关闭时组件返回 `null`，插槽包装元素是 0 尺寸，不挡任何点击。

## 开发脚本

```sh
python preview/embed_artwork.py                  # 重新内嵌三张图（改图后跑）
node   preview/embed-logo.mjs                    # 重新内嵌官方 logo
python preview/validate_art.py                   # 校验预览页里的 SVG 是否可解析
node   ../analysis/theme-surface.mjs             # 重新生成配色可调范围报告
node   ../analysis/palette-defaults.mjs          # 把 22 个旋钮的默认值和已安装应用逐条比对
node   ../analysis/embed-consumers.mjs           # 重新生成"每个旋钮实测改动哪里"的证据块
node   ../analysis/plugin-guards.mjs             # 模板字符串 / package.json / 生成区块的静态守卫
node   ../analysis/fix-css-backticks.mjs         # 修 STYLE_TEXT 里误写的反引号（--check 只报）`nnode   ../analysis/blue-audit.mjs                 # 有没有哪个颜色是"冻住"的：暖色方案下仍然是蓝的
node   ../analysis/pubcheck.mjs                  # 发布就绪清单（--strict 作为发布闸门，--rename 改包名）
```

`fix-css-backticks.mjs` 存在的理由值得写下来：`STYLE_TEXT` 是模板字符串，而 CSS **注释**里引用一个 CSS 单词时最自然的写法就是加反引号——这一个字符会提前结束字符串，让整个 bundle 解析失败。这件事在这个项目里发生过**五次**，每次的报错位置都离真正的改动很远。守卫脚本会先拦下来，这个脚本负责修。规则本身很简单：**那张样式表里不许出现反引号。**

还有一条给自己的：**不要用 PowerShell 脚本去改源码。** 修上面那个反引号问题时，一个 `$t = [System.IO.File]::ReadAllText((Read-Path $p))` 因为 `Read-Path` 不存在而让 `$t` 保持 `$null`，脚本没中断，接着 `WriteAllText($p, $t)` 就把整个 `test/client.test.mjs`（约 10 万字符）写成了空文件。没有 git、没有备份。最后是从 DSH 自己的会话日志（`~/.dsh/sessions/**/session.v4.jsonl.zstd`，6106 个 zstd 帧，解出 26.9 MB 的 JSONL）里把历次 `write`/`edit` 调用重放出来才恢复的——而且重放会漏掉那些当时用 pwsh 做的修改，所以恢复出来的文件有 17 个断言停留在旧版本。结论：**文本改动一律走 edit/write 工具**（有"文件已变"保护），脚本只用来读取和校验。

`palette-defaults.mjs` 是**会失败的**：它从 `client.js` 里把旋钮表读出来，再从已安装的应用里把这些 token 在两个模式下的实际取值解析出来（`var()` 链也会展开），逐条比对，不一致就以非零码退出。手写 44 个十六进制值而没人核对，是那种"看起来对、其实早就不对了"的典型。

`embed-consumers.mjs --check` 只校验不写：生成区块过期就非零码退出。证据过期比没有证据更糟——面板会理直气壮地说"实测改动 53 处"，而应用早就不用那个 token 了。

三个脚本共用 `analysis/lib/asar-css.mjs` 读归档和样式表（asar 头、`unpacked` 处理、`selector{…}` 扫描、类名哈希还原）。`asar-grep.mjs` 也改用了它。顺带记一个 PowerShell 的坑：给原生命令传空字符串参数会被丢掉，`... "" 6` 会变成 `... 6`，于是 `6` 被当成路径过滤条件，结果是"全归档零匹配"——看起来像工具坏了，其实是调用方式。

`plugin-guards.mjs` 守两件 `node --check` 管不到的事，两件都真的踩过：`STYLE_TEXT` 模板字符串里出现反引号（在中文注释里写 CSS 关键字时最容易犯），以及 `package.json` 被加上 UTF-8 BOM 导致 `JSON.parse` 抛错、整个 profile 解析不了插件。

覆盖范围：

- 三层 token 都注册、且调色板里每一项都是成对的 alias token；从没调过色的 profile 里，**第三层必须是空的**（"没碰过就不写"）；
- **弹出层材质是不透明的**：三个填充色都必须是六位十六进制（无 alpha），`--dsw-menu-backdrop-filter` 必须是 `none`；
- 金额格式化：单钱包 / 多钱包累加 / 千分位 / 次分级 / 混合币种 / 零余额；
- 账号缺失与读取异常的降级、客户端元数据字段、折叠态与窄侧栏行为；
- **单击刷新 / 双击充值**：单击要等过双击窗口才发读请求，双击**不得**顺带刷新、且在有 `dshPlatform` 时走原生、没有时走 `window.open`；充值页浮层必须带一个可点的返回控件，关闭后插槽回到 `null`；
- **三张内置图被播种成普通条目**：三个 `img.dsd-bg`、都是 data URI、都带完整的可编辑几何；不在编辑态时图层对辅助技术隐藏；
- **编辑态的隔离罩**：关闭时不存在，进入编辑后出现；图层从 `aria-hidden` 变回可交互并抬到 `z-index: 1x`（正则校验，防止以后被改回 0）；图片挂上拖动与滚轮处理器；
- **`Esc` 由图层负责**：面板不在也能退出；退出后两个 window 监听器都被摘掉；
- **拖动不跳、滚轮缩放**：抓在图片中心再拖 64px（1280px 宽 → 5%）后 `x` 恰好 +5、`y` 不动；松手后再移动指针不会继续移动；滚轮一格 ±4vh 且 `preventDefault`（不许滚动背后的应用）；
- **四个角把手 + 对角锚定**：把手位置由 `size × aspect` 推出（`calc(25% - 40vh)` 这种）；拖东南角 160px 后高度 +64px、`aspect` 不变，并且**反算回西北角的绝对坐标仍是 `(0, 240)`**——即"对角不动"是被验证过的，不是被假设的；
- **宽高比进入模型**：`onLoad` 记下 `naturalWidth / naturalHeight`；重复上报同一个比例不产生写入（否则会自己触发自己）；
- **批量滑杆**：拖「全部透明度」后两张图都变成同值、另一个字段不动、滑杆位置被记住；随后单独调其中一张**只改那一张**，全局值不变；
- **面板可拖动**：拖之前不写死位置（沿用样式表的角落锚点），拖之后落位 `{left, top}`；按在关闭按钮上不触发拖动；
- **存下来的背景图**按各自的 size / x / y / opacity / blur 渲染成 `img.dsd-bg`，且不会把播种的三张混进来；
- **v1 → v2 迁移**：v1 里自己的图保留，内置三张按当时的 `showBuiltin` 决定是否补回；
- **拖滑杆会写回 `localStorage`**，空字符串这类脏值被忽略而不是被 `Number('')` 悄悄写成 0；写图片那份时**不带 `colors` 字段**（两个 key 各自独立）；
- **面板是两栏**：左栏仍是原来的编辑器（文件选择器 + 三张播种图），右栏 22 个旋钮 + 两个开关 + 七个预设 + 恢复默认（无覆盖时禁用）；每个旋钮的 `title` 带 token 全名、实测改动处数/包数和采样到的选择器；底部一行给出覆盖率（本栏 22 / 官方 120 / 51 个包写死颜色）；
- **两个角落按钮读的是本插件自己的 `--dsd-chip-*`**：样式表里 `.dsd-chip` 与 `.dsd-balance` 的底色/描边/文字都来自 `--dsd-chip-*`，且**不再含 `--dsw-alias-bg-module-platform`**（这正是"那个旋钮只改了余额按钮"的根因）；四个角落旋钮都在面板里；注入行内值能让色块显示插件层实际画出的颜色；
- **「应用配色」是真切换**：点深色会调用主题服务的 `setTheme('dark')`（而不是只改编辑对象）；随后服务 publish，面板跟着移动标记、把"正在编辑哪一套"切到深色、并**重新读取**颜色而不是吃上一帧的缓存；外部翻转（设置面板、`跟随系统` 下的系统切换）走同一个事件也能反映出来；而"切换编辑哪一套"**不会**碰应用偏好；
- **护眼绿预设**：底色 `#f4f7ee`/`#101710`、气泡 `#e2ecd6`、文字偏绿近黑、强调 `#4f7d3f`/`#8fc47a`，角落按钮跟着变绿，**状态色不写入**（否则"成功"和"选中"会撞色），每个值都是合法成对颜色；
- **余额芯片自报刷新节奏**：就绪态的 tooltip 必须含「每 15 分钟自动刷新 · 单击立即刷新 · 双击充值」；
- **两处挡住图片的系统表面都被关掉**：样式表里必须有 `span[style*='--dsw-specific-sidebar-fill']{background-color:transparent!important}`（原生窗口按钮那条通道的开关）和 `[class*='composerSeat']{background:transparent!important}`（输入框座位）；同时断言本插件**没有**去动应用自己的输入框卡片；
- **编辑用的部件退出窗口拖动区**：`.dsd-layer[data-editing='true']` 与 `.dsd-editor` 都带 `-webkit-app-region:no-drag`；
- **面板不会被停到窗口按钮底下**：标题栏 40px 时把面板往上方拖，落点被夹到 `y=44`；修好之前存下的 `y=6` 在渲染时被拉到 `44`；而**没有**标题栏（macOS/Linux）时同一个 `y=6` 被原样尊重；
- **「更多图片」是一次浏览器跳转**：点击前不打开任何东西，点击后 `window.open` 收到 `https://ai-meme.cdqyfdbymn.me` 且 `target=_blank`；布局是 `2fr 1fr`，两个按钮同为 28px 高，且"添加图片"是实心、"更多图片"是描边；
- **一个旋钮写一对值**：只改浅色时，层里那个 token 的深色是**记录下来的默认值**，不是被编辑传染的值；层里只出现碰过的 token；
- **浅/深开关决定写哪一个**：切到深色后输入框显示的是深色默认值（不是刚敲的浅色值），两边可以分别设；
- **半成品不落盘**：`#41` 只进草稿、层和存储都不动，输入框显示 `#41` 而不是弹回原值；补齐第 6 位才提交；失焦丢弃草稿；
- **调色盘保留 alpha**：`#1d4ed80f` 的旋钮在调色盘里显示 `#1d4ed8`，换成绿色后写进层的是 `#00ff000f`；
- **单个旋钮可以只还原自己**，其余覆盖不受影响；被还原的 token 是**从层里消失**，而不是被写成一份默认值的副本（否则别的皮肤的值永远透不过来）；
- **预设一次写 19 个旋钮值**（含自带皮肤不碰的侧栏与气泡），每个值都是合法成对颜色；写完还能接着单个改；「恢复默认」把层清空、存储清成 `{}`、按钮重新禁用；
- **重启后颜色还在**：启动时读存储并推一次，所以首屏就是对的；存储里的脏 key、非颜色值会被丢掉，下一次写入只保留合法旋钮；
- **关闭插件会收回颜色层**（和自带品牌层一样），否则会留下一套没人能撤销的颜色；
- **无关的 store 变化不重新发布主题**：半成品输入和"选中一张图片"都会触发订阅，但层不重推——这是拖图片时每帧重写几百个行内属性的那道闸。
- **色块显示的是页面上真实的颜色**：行内值优先于 `getComputedStyle`，两者都优先于插件记录的表；`rgb()` / `rgba()` 会被换算成十六进制（含 alpha），而 `color-mix()` 这类换算不出来的值**退回记录的默认值**，不会假装成一个十六进制；用户自己设过的值优先于两者。18 行的读取按主题的 `revision` 缓存了一次，所以拖图片时不会每帧重读 18 遍计算样式。

## 已知限制

- 暗色模式的藏青底色是刻意偏离原有中性色的设计选择；如果你更想要原汁原味的中性灰，删掉 `BRAND_TOKENS` 里 `--dsw-alias-bg-*` 那几个条目即可，只保留交互蓝。
- **配色栏是认得出来的一批，不是 401 个 token。** 这是取舍：能量的是"界面上认得出来的地方"，不是"所有能改的东西"。这些旋钮全部来自实测消费方最多的那批 token（见 [THEME-SURFACE.md](THEME-SURFACE.md) 第 3 节）。想加旋钮就往 `COLOR_SLOTS` 里加一条，报告和校验会跟着更新。
- **只改一种模式时，另一种模式用记录下来的默认值**。能读到的一侧是**页面上真实的颜色**（包括别的皮肤设的），读不到的那一侧只能退到插件记录的表。所以如果你装了第三方皮肤又只改了深色、然后切到浅色，那个 token 的浅色会回到"本插件默认的样子"而不是那个皮肤的样子。两侧都设一次就没有这个问题。
- 余额数字来自 Platform 接口按需拉取，不是实时流，因此可能与你刚充值的金额有几秒到几分钟的偏差；点一下芯片可立即刷新。
- **图片现在真的在应用底下**（`z-index:-1`），代价是它只能出现在应用自己留空的地方。画面主体已经全部让开：应用外框、中间那一列画布、会话列自己的 root，以及**左侧栏**（列本身 + 里面那个 root + Windows 顶部那条标题栏）。**卡片、输入框仍保留各自的不透明底色**——面板浮在壁纸之上本来就是对的，想让它们也透出来就把对应旋钮设成带 alpha 的值（输入框接受 8 位）。另外这一层靠 `[class*='frame']:has([class*='sidebarCol'])`、`[class*='root']:has([class*='newSession'])` 这类选择器认应用的表面，**宿主大改版后这里应当重新核对**（`analysis/theme-surface.mjs` 会重新列出实际的类名与消费方）。
- **侧栏的颜色衬在图片下面，而不是盖在上面。** 第一版是给侧栏加一层 45% 的薄纱：侧栏认得出来，但图片被冲淡了——用户的原话是"薄纱是为了让人能看出侧边栏的存在（应当保留！），但代价是图片显得被盖住了"。两件事其实可以同时成立，只要**把颜色挪到壁纸的另一侧**：侧栏那两层的底色全部透明，改为在**图片层里、所有图片之前**画一块"床"（`.dsd-side`，颜色就是原来的 `--dsw-specific-sidebar-fill`，位置和宽度由 `trackComposerPane` 顺手量出来）。于是：图片保持完整强度，而侧栏与主界面的区别由**图片底下的底色**加上一条**在图片之上的发丝线**（`.dsd-side-line`，1px，用「边框与分隔线」那个旋钮的颜色）承担——图片调到 100% 不透明时，那条线仍然在。Windows 顶部那一条用的是同一个 token，但它既不要床也不要线：那里没有侧栏，只有图片。
  **会话列表底部那条滚动渐隐要关掉。** 它是 `[workspace] .fade`：从透明渐变到侧栏底色，画在图片**之上**，用来让列表滚出视野时淡出。颜色挪到图片下面之后它就多余了，而在它还在的时候，它的不透明末端正好落在两个角落按钮上方——用户看到的就是"按钮上沿有一条分界线"。 应用给输入区留了一小块下边距，座位（seat）的盒子到那里就结束了；只按座位的高度铺遮挡层，正文会从那道缝里露出来（用户报过"输出框下方的正文又露出来了"）。所以带子的高度是 `座位高度 + 座位离窗口底部的距离`，下边缘钉在窗口底部而不是座位底部——图片的第二份也用同一个 `clip-path`，两处始终是同一个矩形。
- **带子的上边缘要整体渐隐，不能只让遮挡层渐隐。** 这是用户报的第二处：输入框上方能看到一条明显的分界线，上下图片颜色不一致。原因是遮挡层必须"大部分不透明"（这样才挡得住正文）但"顶部要软"（否则正文被切成一条硬边），而**半透明的遮挡层会让背后的壁纸透出来，同时上面那份图片副本照样全强度画着**——同一张图在渐隐的 44px 里被画了两次，多出来的那一份就是那条亮线。修法是把遮挡层和图片副本**包进同一个容器、用一条 `mask-image` 一起渐隐**：顶部只有壁纸，下面只有副本，中间按比例互补，加起来永远恰好是一张图。
- **带子只在输入框"贴底"的时候才铺。** 这是用户报的界面级 bug：**开新会话时整页只剩背景图片**。新会话页把输入框摆在页面**正中**，而原来的判断只看"座位有没有、大不大"，没看"在不在底部"——于是那条本该挡住下滚正文的遮挡带，横铺在了整张首屏上。判据现在是**离窗口底部多远**，并且用窗口高度的比例（贴底大约 20px，居中则是几百 px），这样任何分辨率都成立。
- **去白底：改哪个旋钮就存哪个旋钮，原图保留。** 技术核心是**从四边向内漫水填充**：从图片边框开始扩展，只穿过接近白色的像素，所以**主体内部的白色（围裙、眼睛高光）会留下**——这是"填充"和"全局阈值"的全部区别，也是它值得这些代码的原因。填充用**扫描线**实现（每个种子沿本行左右走到底），空白区域只占一个栈位而不是每像素一个，这是"能不能感觉到卡"的分界。
  拖动参数时跑的是**粗一档**（长边 560），所以结果两帧内到手、滑杆是黏在图上的；松手 280ms 之后才跑**全分辨率**那遍，被取代的那遍用序号自己作废，快速拖动不会把旧结果盖上去。
  **这一版最初做成"试看 → 按一下才落盘"，后来那个按钮被删掉了**（理由见下面"原图留下来"那一条）：现在旋钮改动直接写进 `item.key`，全分辨率那遍替换 `src` 并落盘，粗那遍只当屏幕上的临时替身。存成品实测**+61%**，留着原图再翻一倍（数字来自 `analysis/white-keying-cost.py`）。透明区域的 RGB 会被填成纯白：那些像素看不见但**照样要编码**，把旧背景留在透明底下等于为同一份细节付两次钱。
- **A 和 B 终于量了，不是推理的。** 之前我一直说"存原图重算会拖慢启动"，却从没测过。用户问"我们是不是从来没直观对比过"，确实没有，所以补了一条基准测试（`the cut fits the frame budget on a full-size picture`），用一张合成的"照片感"图（1600×1000：带噪声的近白背景 + 主体 + 几条细线；填充的代价取决于"要停几次重开"，平坦的白底测的是最容易的情况）：

  | | 存成品（A，已实现） | 存原图每次重算（B） |
  |---|---|---|
  | 启动代价 | **0 ms** | 每张去白底的图 **~114 ms** → 十六张约 **1.8 s**，**每次启动** |
  | 存储 | 每张 +61% | 不变 |
  | 想改参数 | 得重新添加那张图 | 随时可调 |

  粗那遍（0.2MP）约 30–40 ms，所以拖动是跟手的；全分辨率（1.6MP）大约 100 ms，作为一次主动操作完全没问题——但**乘八、再乘"每次启动"就变成用户会感觉到的东西**，而且它会落在应用自己也在加载的那一秒里。测试里留了两条宽松上限（粗 <400ms、全 <1200ms，后者扣掉 280ms 的静默等待）当护栏，免得以后哪次改动让填充慢一个数量级而没人发现。
- **"应用并保存"这个按钮被删掉了，原图留下来。** 第一版我做成"试看 → 按一下才落盘"，理由是想省存储：落盘之后原图就没用了。用户的回答是"应当保留用户在原图基础上继续调节的权利"——他是对的，而且这不是一个存储问题：**取消那个按钮省下的不是空间，是权限**。
  现在的模型是：一张被切过的图身上有两样东西——`src`（切好的，用来画）和 `original`（当初导入的那份，用来重切）。旋钮改动直接写进 `item.key`，**没有确认步骤**；粗那遍只当屏幕上的临时替身，全分辨率那遍才替换 `src` 并落盘（防抖 280ms）。取消勾选就把 `src` 换回 `original` 并丢掉 `key`，那份副本也就释放了。
  代价是**每张切过的图要存两份**（约 +122%）。**这个代价后来被证明远没有我当时说的那么要紧**——见下面关于上限的那一条：真实的可用空间是 32 MB 量级，满十六张图连备份大约占 13%，每次保存要给这 4 MB 做一次序列化，实测 **6.7 ms**。
- **两个手工修正旋钮，对着的正是"复杂边缘判定不准"。** 用户看过第一版之后的反馈是：边缘复杂的地方（头发、蕾丝、气泡框）切得不干净。这不是容差调不好，而是**有两类相反的误差**，一个滑杆治不了两种病：
  - **收边 / 扩边（±3px）**：留下白边就往里收，啃进主体就往外放。实现是掩膜的一遍**膨胀 / 腐蚀**（3×3），每遍移动一个整像素。腐蚀那一版我写错过：第一版写成"没有掩膜邻居就置 1"，等于把整张图填满——正确的腐蚀是"掩膜像素只有在**邻居全是掩膜**时才留下"。
  - **柔和边缘被砍掉了。** 我做过第三个旋钮：alpha 不再 0/255 两档，而是按"有多白"算出来。用户的判词是"纯纯副作用"——背景稍微不均匀，它就留下一层很淡的、到处都是的影，而真正的复杂边缘该不该留白本来就该由**收边**决定。**一个能看出副作用的旋钮不如没有旋钮**，所以它连同代码一起删掉了，而不是留一个默认关着的开关。
  两个旋钮和容差是三路独立的输入，改任一个都会带上另外两个当前的值重算（`requestKeyPreview` 里先合并再排队）。
- **上限是量出来的，不是引用的——而量出来之后，我原来的说法错了 6 倍。** 我在面板和文档里都写过"Chromium 通常 5 MB"，那是**没有验证过的数字**。用户当场指出："有办法确定一个真实的上限吗，我们不能拿一个可能不存在或者不准确的限额欺骗用户。"
  浏览器不公开这个配额，**唯一诚实的办法是真的去写，写到它拒绝为止**。所以读数条上有一个按钮：二分查找（约九次写入，每次比上一次大一倍、互相覆盖，所以峰值就是一个字符串，结束时一次 `removeItem` 清掉），把最大的**写得进去**的长度记下来，存进 `dsd:quota:v1`——配额是来源的属性，不是会话的属性，量一次就够，之后按钮变成「重测」。
  它是**用户主动点的**，因为测量不是免费的：那零点几秒里存储是真的满的，任何想写数据的东西（包括本插件自己）会被拒绝一次。这条写在按钮的 tooltip 里，不藏在代码里。
  单位用**字符**而不是字节：读数条本来就这么记账，所以无论浏览器内部乘几，显示的百分比都是准的；没测之前面板说的是"上限未测"，**不编一个数**。
  **实测结果：31.9 MB（33,488,896 字符）。** 我猜的 5 MB 差了 6.4 倍。这个数字本身还说明了一件事：**我之前所有关于"存储紧张"的取舍叙述都是错的**——留原图、存两份、+61% / +122% 这些百分比虽然都对，但它们的分母根本不是我以为的那个。八张图连备份约 2.9 MB，占 **9%**。教训不是"要量"，而是**我拿一个没量过的数当成约束，然后在它上面做了一串设计决定**。
  读数条现在回答用户真正问的两个问题：**我塞进去的图占了多少**（图片 = 原图 + 备份）、**还剩多少**（余量 = 上限 − 本插件占用 − 应用其它数据，带百分比）。完整拆分（其中原图备份多少、本插件其它数据多少、应用其它数据多少、上限多少）在那一行的 tooltip 里。
  按钮不会消失——第一版量完就把按钮藏起来，用户的评价是"然后按钮消失，什么都做不了了"；现在它变成「重测」，而问题变成了这一行有没有回答"还剩多少"。
- **上限从 8 放宽到 16。** 定 8 的时候我以为存储紧张（错，见上），所以它一直是个"空间"决定；现在理由只剩编辑面板的长度，那就不该拦着人。满十六张、每张都留备份的情况下：payload **4.07 MB**（占 32 MB 上限的 13%），每次保存的序列化 **6.7 ms**（实测，`JSON.stringify` 整个列表——localStorage 没有局部写，改一张要重写全部）。这两个数都在"感觉不到"的量级，所以放宽是安全的；真正会先撑不住的其实是面板的滚动长度，不是存储。
- **存储用量是读出来的，不是猜的。** 面板报的是能知道的东西：本插件占了多少、同一存储里其它数据占了多少（按浏览器记账的方式算：UTF-16 码元，而 data URI 是 ASCII，所以一个码元就是一个字符）。上限到了会明确提示（含壁纸在内最多 16 张），不会静默失败。
- **面板会挡住中间的图，所以图的控制得能跟着图走。** 用户的要求：把面板拖到下面藏起来，以便在屏幕中央操作图片——那"调图"这件事就不能只住在面板里。于是**右键图片**会在它旁边开一个小窗口，内容与面板里那张图的一段**完全一样**（同一个 `PictureControls` 组件，写两遍一定会走样）。位置在渲染时用图片自己的 `getBoundingClientRect()` 量，所以拖动之后它跟着走；量不到（测试环境、还没挂载）就退回左上角，而不是拿模型里的百分比猜一个屏幕坐标。Esc 一次只关一层：先小窗口，再退出编辑——把两层一起关掉，这个小窗口就成了陷阱。
- **大小和位置的三条滑杆彻底删掉了，连小窗口里也没有。** 既然拖拽和滚轮已经能直接改，它们只是在拉长面板（用户的原话是"背景菜单的滚动长度也会有所缓解"）；后来用户又明确了一次"可以直接删掉了，用手调整的功能已够用"。代价要写清楚：**现在没有任何输入框能精确设定尺寸或坐标**，只有拖动、滚轮、四角拉伸。
- **"操作哪张图，哪张图的框就该亮着"——一个动作，一种含义。** 用户报的两件事其实是同一件：操作新图片时，上一张的右键小窗口该消失；面板里正在操作的那一行该亮起来（列表有十六张时还该滚进视野）。所以它们合成一个 `touchPicture(id)`：面板的摇杆、小窗口、直接在画布上拖/滚/拉角、去白底开关——所有"动这张图"的入口都调它，它做两件事：把 `selected` 指过去（行亮、画布上的虚线框跟过去、必要时滚进视野），以及**关掉别的图片的小窗口**（同 id 的留着，那就是你正在操作的那张）。一个动作只有一种含义，才不会出现"我明明在改 B，A 的窗口还挂在那里"。
- **输入框上方那块白色：带子里的第二份图，把壁纸画成了贴纸。** 用户的猜测很准（"估计还是图片放在具体哪个高度的问题"）。带子（`.dsd-band`）里有一份图片副本，用来盖住输入框那一条里应用自己画的不透明背景；它给**每一张**图都用了贴纸样式（`pictureStyle`：`height: size vh` + `left/top` 百分比），于是一张"整图壁纸"在那里变成窗口中间一个 60vh 的方框，其余地方露出 veil 的纯底色——浅色模式下就是**一整块白**。只有贴纸时看不出来，因为那时底色和应用自己的背景同色；一放壁纸，两者的差别就是那块白。修法：带子里按 `item.full` 分别用 `fullStyle` / `pictureStyle`，并给副本加一个**独有的** `data-band-item`（不能复用 `data-item-id`：小窗口正是靠后者去问"这张图真实的框在哪"，而每张图有两个副本）。
- **动图：宁可文件大，也不要静悄悄变成静图。** 导入管线本来会把"长边超过 1600 或大于 400 KB"的图过一遍 canvas（缩到 1600px 的 WebP）——而 canvas 只有一帧，所以一张 GIF 会**悄无声息地变成静图**，用户只会觉得"我加的动图怎么不动了"。修法是在进 canvas 之前分流：`data:image/gif` 开头的一律**原样保存**，不缩放、不重编码。更大的文件是这两个结果里较好的那个，何况现在知道上限是 32 MB。
  配套的一半是诚实：**动图的"去白底"开关是禁用的**（title 写原因："动图每一帧都要处理"）。给一个按下去就把动画压平的开关，比没有这个开关更坏。
  已知边界：只有 GIF 能从 data URI 前缀认出来；**动图 WebP** 和静态 WebP 长得一样，所以它只在"小到不需要过 canvas"时才保住动画。这条写在函数的注释里，不假装完整。
- **小窗口的四次修正，都是"它站在别人的地盘上"这一类问题。** 用户一次报了三件：① 底色不透明（半透明的 popover 材质让底下的文字透上来）；② 面板应该盖在小窗口上方（原来小窗口在面板上面）；③ 图片拖到最右时窗口压在自己的图上；④ 壁纸的小窗口开在右上角，正好压住窗口的最小化/关闭按钮。
  ①② 是取值问题：小窗口改用 `--dsw-alias-bg-base`（面板同款，不透明）并把 `z-index` 从 1003 降到 **1001**，低于面板的 1002。
  ③ 是位置算法：从"永远放右边"改成**先右、再左、再下、再上**，每一种都要真的放得下才用——图片贴到右边缘时，窗口就到它左边去；两边都不够就挪到上下。位置在渲染时用图片自己的 `getBoundingClientRect()` 量，所以跟着图片走。
  ④ 是默认位置：壁纸**没有"旁边"**（它就是整个窗口），所以它的窗口固定在**左侧垂直居中**——聊天窗口上唯一一块既没有文字、也没有窗口按钮的地方。
  另外小窗口现在可以**拖**（拖标题栏），拖过之后那个位置一直有效到关闭为止：人是故意挪的。
- **"点完重测没有反应"是反馈缺失。** 重测之后那行数字几乎不变（本来就知道上限了），所以看起来像什么都没发生。现在按钮点完会变成「**已刷新**」，三秒后变回「重测」——用按钮自己说话，而不是再往面板里塞一行字（那正是上一轮把读数挤出视口的做法）。
- **那一行和它的 tooltip 是同一笔账的两端。** 行上只有两个数（图片、余量），tooltip 里是四个数，中间少了"已用"这一项，所以看起来像两组无关的读数。现在 tooltip 把算式写全：`图片 0.7 MB（含原图备份 0.4 MB）+ 本插件其它 3 KB + 应用其它 62 KB = 已用 0.8 MB；上限 31.9 MB（实测）− 已用 = 余量 31.1 MB`。
- **提示文案只写用户需要的那一句。** 用户的批注是"toolkit 不用写那么多，只写用户有必要看到的东西"。我原来的 tooltip 里混了三类东西：使用者需要的信息（上限多少、备份占多少）、只对维护者有意义的信息（"探针"、"二分查找"、"如果这时应用要写数据那一次可能失败"）、以及我自己的判断过程。第三类全删，第二类压缩成一句真正的代价说明（"量的时候会短暂占满本地存储，然后立刻恢复"），第一类只留数字。同样被压缩的还有面板里的说明段落：颜色那两条从三行压到一行，编辑态的引导从两句压到一句。
- **"重测之后读数不见了"不是显示问题，是布局问题。** 用户报的是"点击重测应该是刷新前面的值，而不是跳转到实测上限约 31.9 MB，必须关闭背景按钮再打开才能恢复"。原因：测量成功后会往面板末尾塞一条 notice，而面板是"头部固定 + 身体滚动"的纵向 flex——notice 一进来就挤掉身体的高度，读数那一行（身体里的最后一项）被推出可视区；关闭再打开会重置滚动位置，所以看起来像"恢复了"。修法有两层：**测量成功后不再发 notice**（那行自己就从"上限未测"变成了"余量 31.1 MB（97%）"，那才是用户要看的），以及**notice 改成绝对定位**（状态提示不该让面板重排）。
- **带子的位置要跟着页面变，而且量不到座位时必须四边清零。** 尺寸观察者只在"大小变了"时触发；**从一个页面走到另一个页面**（比如打开插件页）时座位消失、什么都没有 resize，于是带子留在原地——一块不透明的面板压在下一页的底部，指针还能穿过去点到底下的按钮，用户只能靠猜。而且它看起来是"偶发"的：第二次进来时某个 resize 已经顺手修正了它。修法有三层：① 用 `MutationObserver` 盯住 `body`（合并到每帧一次写入，所以对话再忙也只是一次查询）；② 量不到座位时**四个变量全部清零**，而不是只清高度——因为遮挡层的高度是 `pane-bottom + pane-height`，残留的 bottom 会在下一页留下一整条不透明带；③ `--dsd-pane-left` 永远不小于侧栏右边缘，这样任何一次过期或异常的测量都不可能横跨过去盖住左下角那两个按钮。
- **原生标题栏按钮压住了应用的图片预览关闭键——而且点错会关掉整个应用。** 预览的关闭键是 `position:fixed; top:20px; right:20px; 36×36`，Windows 的标题栏条是 40px 高，所以它一直有一半在原生按钮底下，只是以前那条带子不透明、看不出来。**页面里的任何东西都盖不过原生覆盖层**，只能把按钮往下挪。
  第一版用 CSS 猜选择器，**没生效**：那个按钮所在的样式表在归档里是分块的，选择器读不全——`maskDrop` 其实是我从一段被截断的文本里推断出来的名字，它并不存在。
  现在改成**在 JS 里按形状认**（`trackOverlayChrome`）：`position:fixed` + `top/right: 20px` + `36×36`。这个界面里没有第二个控件是这个形状，所以不需要知道类名。`MutationObserver` 盯着 `body` 的直接子节点（应用的浮层都是 portal 到 `body` 的），浮层一出现就扫一遍；已经挪过的不会再叠加（挪过之后计算出来的 `top` 就是 60px，签名不再匹配）。没有标题栏的平台整段是空操作。
- **整图壁纸是同一个模型里的 `full: true`。** 它和贴纸共用一份列表，区别只在渲染：铺满视口、`object-fit: cover`、没有边缘蒙版、没有位置和大小可言（所以不能拖、没有四角把手，编辑器里也只给透明度和模糊两个滑杆）。它靠**渲染顺序**而不是 `z-index` 垫在最下面：基图先画，贴纸后画——模型里的先后顺序是用户添加的顺序，而"壁纸在底下"不该由它决定。同一时间只保留一张：再添加一张会替换掉原来那张（否则第二张永远看不见，读起来像"添加没反应"）。
- 图片层、编辑器、充值页宿主都 portal 到 `document.body`，因此**在每一页都在**（包括「新会话」和「插件」页）。若某个宿主拿不到 `react-dom`（`createPortal` 不可用），四者会退回就地渲染：图片会落进 `shell.overlay` 那一层（`z-index: 20`），看起来会盖住侧栏。
- 拉伸现在用的是**四个角**的把手，对角固定。代价是每张图必须在模型里存一个 `aspect`（由图片解码时测出）。如果某张图的 `src` 是不可解码的（比如坏掉的 data URI），`aspect` 会停在默认值 `1`，那张图的把手位置和缩放比例就会偏——但拖动本身不会坏。
- 背景图存在**浏览器级** `localStorage` 里，所以换一个浏览器/Web 端看就是另一套；同一台机器的桌面应用内是持久的。不写 profile，因此卸载插件不会顺手删掉你的图。**面板位置和两个全局滑杆的值也存在同一份状态里。**
- 自己加的图会被压到长边 1600px 的 webp，超大图的细节会有损；这是为了不撑爆配额，属于刻意取舍。**动图是例外**：GIF 原样保存、不缩放，所以它可能明显更大（一张动图占几 MB 很正常）。
- **动图不能去白底。** 去白底跑在 canvas 上，而 canvas 只有一帧，硬做会把动图压成静图；所以那个开关对 GIF 是禁用的，鼠标停上去写着原因。
- **没有输入框能精确设定大小和坐标。** 这是刻意的：拖拽、滚轮、四角拉伸已经够用，三条滑杆只是在拉长面板（见下文）。要"精确到 50vh"目前没有入口。
- **只在 Windows + 已安装的这个 DSH 版本上验证过。** 标题栏那条修正只在 `data-windows-titlebar` 存在时生效，其他平台是空操作；macOS / Linux 上"预览关闭键被窗口按钮压住"这个问题是否存在、以及是否已经解决，**未经验证**。
- **深色模式下，浅色底图去白底后仍可能留一点边。** 这是透明度数学的问题（半透明像素和深色背景混色），不是算法能完全消除的；浅色图配深色背景时更明显。
- 编辑期间整块界面被隔离罩挡住——这是你要的效果，但代价是**侧栏上那个「背景」按钮也点不到了**，退出只能靠面板的 ✕ 或 `Esc`（后者由图层注册，面板即使出问题也仍然有效）。面板本身可以拖到任何位置，所以"它挡住我要调的地方"这条已经解决。
- 「双击充值」走的是宿主原生 `WebContentsView`。若某个宿主的 `dshPlatform` 行为与官方 `ui-settings-account` 不一致，失败时留在状态页并给「重试 / 在浏览器打开」，不会把界面卡住。
- 弹出层材质被全局改成不透明后，**官方所有 `MenuSurface` 菜单都不再是毛玻璃**。这是修"看不清"的直接代价；不喜欢就删掉 `MATERIAL_TOKENS` 那一层（它和调色板是独立的两个 `overrideTokens` source）。
- 表情包图片自带文字气泡，作为背景时会带上那行字。觉得太抢眼就删掉那个条目，或在编辑器里压低它的透明度。
- 图片和 logo 都是内嵌的 base64，`client.js` 因此约 **482 KB**；这是「服务端不伺服包内静态文件」的必然代价（官方 logo 的那 3.4 KB path 同理）。

## 发布（作为一个 DSH 插件）

这个包是**按可发布来写的**，不是一个只在本机跑得起来的草稿。"可发布"在这里是一份可以机械校验的清单，`analysis/pubcheck.mjs` 就是那份清单：

```sh
node analysis/pubcheck.mjs            # 出报告；结构性错误才非零退出
node analysis/pubcheck.mjs --strict   # 发布闸门：还有待办项就非零退出
```

它真正在防的几件事，都是"错了会很难查"的那种：

- **包名必须四处一致。** 浏览器半在 `window.__ModuleLoader__.load({ id })` 里用这个 id 注册自己，`PLUGIN_ID` 用它给主题层命名，`cordis.patch.yml` 的插件行也写着它。任何一处不一致，症状是**插件静默不挂载**——没有报错，只是什么都没发生。
- **不许有 `@deepseek-ai/*` 依赖。** 尤其是 `@deepseek-ai/schemastery`：它没有跟随 DSH 安装一起发布，声明它会让 profile 的包管理器去 registry 找一个可能和运行版本对不上的版本，而**一个坏掉的 profile 依赖会让整个 profile 起不来**。所以本插件声明零依赖，所有取值写死在代码里，可调项都在这个 README 里。
- **`files` 白名单**必须覆盖全部运行时文件，且不许把 `test/`、`preview/`、`analysis/` 发出去。
- **不许泄漏开发机的绝对路径**（这条真的抓到过两次：一次是安装说明里写着我的工作目录，另一次是这句说明本身把那个路径当例子写了进来——扫文档的检查，最容易被解释它的那段话绊倒）。
- **README 里引用的测试数量必须和测试文件对上**——那是文档里唯一一个读者无法凭阅读验证的数字。

当前状态：**0 个结构性错误，3 个发布前待办**。清单在这里，连同每项归谁：

### 这个包的形状

- `client.js` 约 **482 KB**，其中绝大部分是内嵌的三张图的 base64。它是整个浏览器半，也是整个 UI——宿主半（`index.js`）是空的，只为了让 Loader 有一行可解析的宿主插件。

### 加载失败时的排查入口

最直接的一步是查启动清单里有没有本插件：

```js
JSON.stringify(window.__DSH_BOOT__).includes('dsh-diy-skin')
```

返回 `false` 就说明宿主半侧没挂载，后面一切都不用查了（历史上就是 `name` 写了目录而非入口文件）。

`apply` 还会往控制台打两行标记，但界面走 Electron 的 `dsh-app://` 载体时它们落在主进程日志而不是页面控制台，所以**以启动清单为准**：

```
[deepseek-decor] client half loaded
[deepseek-decor] brand palette applied (50 tokens)
[deepseek-decor] popup material made opaque (4 tokens)
```

### 为什么 `theme` 必须写进 inject

这一条我一开始判断反了，值得记下来。我原以为 `inject` 列出的服务是硬依赖——缺一个就静默不激活——于是把它缩减成三项来"加固"。

**实际上恰好相反**：在这个框架里，把服务名放进 `inject` 正是**等待该服务就绪**的方式。官方 `settings-account` 客户端就声明了 `["slots","locale","remote","remote.account","theme","configForms"]`。我把 `theme` 删掉后，`apply` 跑得比主题服务注册更早，`ctx.theme` 还是空的，于是调色板层从未注册——**界面颜色完全没变，且没有任何报错**。

所以正确的写法是**声明** `theme` / `remote.account`，同时在调用处仍按需解析（`ctx.remote.account` 可能与 `remote` 不同时存在），做到"等到就绪"与"缺了也不崩"两者兼顾。

### 插槽选择的实测经验

- **`sidebar.toggle.badge` 是单占用者**。图片层和折叠徽标同时注册进这个插槽时，只有先注册的生效，另一个**被静默丢弃**。图片层因此不在这个插槽里——它现在是 root 作用域 portal 到 `document.body` 的一个固定层。
- **CSS 自定义属性要同时声明在 `:root` 和 `body`**。主题 presenter 把 alias token 作为**内联自定义属性写在 `body` 上**（`body[style="--dsw-alias-*: …"]`），而 `body` 作用域的声明优先级高于 `:root`。只写 `:root` 时，落在 body 上的属性会遮蔽它。按下不再需要这条：三张图改成条目后，data URI 是 `<img src>` 而不是自定义属性。
- **`shell.overlay` 是 root 作用域的列表插槽**，所在层 `z-index:20; pointer-events:none`，而 `>*{pointer-events:auto}`。它适合放"全视口但不常驻"的东西：组件关闭时返回 `null`，插槽包装元素就是 0 尺寸，不挡任何点击。**但它不适合当背景**：那一层在侧栏之上，图片放进去会盖住界面。背景层要 portal 到 `document.body` 才落在 `z-index: 0`。
- **帧内赢不了标题栏**。`overlayLayer` 最高 `z-index: 20`，而 Windows 标题栏是应用自己的 DOM（`.frame:before` 画拖拽带，高度由 `--dsh-windows-titlebar-height` 公布）。任何要与标题栏共存的全屏浮层都得 portal 到 body 并用这个变量留白。
- **插槽占用者要是"纯元素工厂"**。注册进插槽的组件如果是 `useState` 的拥有者，在测试台里直接调用它会崩（hook 需要 React 的渲染上下文）。本插件所有注册点都包了一层薄壳（`function X(){ return h(Real) }`），hook 只经 React 自己的渲染进入。
- **一次 `loadPlugin` 一套 React 桩**。测试台每次 `loadPlugin` 都会新建 harness，所以第二次加载的组件必须用**它自己的** `render` 走一遍——混用两个实例会让 hook 拥有者对不上，报的却是莫名其妙的 `Cannot read properties of undefined`。
- **hook 不能在提前返回之后**。这是本插件唯一一次造成"界面卡死、无法退出"的事故，详见 [第 3 节那个陷阱](#一个把面板彻底搞没了的-react-陷阱)。规则很简单：组件里所有 hook 都写在第一个 `return` 之前，副作用该由"永远挂载的那个组件"承担。测试台现在会强制这条规则。
- **模板字符串里的 CSS 注释不能出现反引号**。`STYLE_TEXT` 是一个模板字符串，注释里写 `` `fixed` `` 会直接把它闭合掉——我这次就这么踩了两回，症状是模块整段语法错误、测试全红。`node --check` 是发现它的最快方式。

## 发布流程（每次发新版）

前提：开发时 profile 里那一行的值是 `link:…`（指回这个工作目录），所以改代码重启即生效。

1. **改代码**（`client.js` + `test/client.test.mjs`），重启应用肉眼确认。
2. **升版本号**：`dsh-diy-skin/package.json`。修 bug 升末位（`1.30.1`），加功能升中位（`1.31.0`）。
   **npm 拒绝发布已存在的版本**，所以这一步不能跳。
3. **跑校验**：`node analysis/pubcheck.mjs --strict` 要 0 项待办；`node dsh-diy-skin/test/client.test.mjs` 全绿；
   另外 `plugin-guards` / `blue-audit` / `palette-defaults` / `embed-consumers --check` 四条。
4. **提交并推送**。
5. **发布**：
   - 手动：`cd dsh-diy-skin && npm publish`（会走一次 security key 的浏览器确认）。
   - 自动（已配好 workflow `.github/workflows/publish.yml`）：`git tag v1.31.0 && git push --tags`，
     GitHub Actions 用 trusted publishing 发布，**不需要 token、不需要 OTP**。tag 上的版本必须和
     `package.json` 里的一致。
6. **验一次发布物**：读 `https://registry.npmjs.org/dsh-diy-skin/latest`，核对 `version`、
   `license`、有没有 `dependencies`、以及 `dist.shasum` 是否和 `npm publish` 输出的那串一致。
   最彻底的一次是临时把 profile 那一行改成 `"dsh-diy-skin": "^1.31.0"` + `pnpm install --dir <profile>`，
   重启看它能不能从 npm 装起来 —— 验完记得改回 `link:`。

**用户不会自动拿到新版**：他们那条依赖是 `^1.30.0` 这样的范围，要在「插件」面板里更新/重装才会拉新的。
这是好事 —— 发坏了不会瞬间推给所有人。

**为什么不用 `pnpm.overrides` 把"版本范围"指向本地**：试过了，这个 pnpm 版本不接受 override 里的
`link:`（装完之后 `node_modules/dsh-diy-skin` 没有 LinkType，是真实拷贝）。所以只能二选一，
而"别人能按名字装"是**包的属性**，不取决于自己 profile 怎么写。
