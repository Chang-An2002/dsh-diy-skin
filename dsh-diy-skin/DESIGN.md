# 设计记录

这份文件是给想改这个插件的人（包括未来的我）看的：每个决定为什么这么做、试错过什么、哪些数字是量出来的。

用户要看的安装与使用在 [README.md](README.md)；每个颜色旋钮对应界面上哪一处，在 [KNOB-REACH.md](KNOB-REACH.md)；应用自身的可调 token 全景在 [THEME-SURFACE.md](THEME-SURFACE.md)。

## 目录结构

```
package.json        包清单：exports、dsh.bundle.patch、dsh.client
cordis.patch.yml    向 profile 插入本插件的一行
index.js            宿主半侧（无行为，仅供 Loader 解析出插件行）
client.js           浏览器半侧：调色板 + 弹出层材质 + 背景图层与编辑器 + 余额芯片与充值页宿主
icon.svg            插件管理器卡片图标
THEME-SURFACE.md    界面配色可调范围（由脚本从已安装应用里读出后生成）
test/client.test.mjs 行为测试
preview/            工具脚本（内嵌素材、安装、校验）
```

`client.js` 里有两个生成区块，都由脚本就地重写，不要手工编辑那段数据：

- `@dsd-artwork` —— 三张角色图的 base64（约 240 KB），由 `preview/embed_artwork.py` 生成；
- `@dsd-logo` —— 官方那条鱼的 SVG path（3.4 KB），由 `preview/embed-logo.mjs` 从**已安装的** `dsh-client-ui-primitives` 里读出来（那个包专门导出 `FISH_LOGO_PATH` / `FISH_LOGO_VIEWBOX` 给需要自己拼 svg 的消费方），所以它不会和界面其它地方画的那条鱼跑偏。

`COLOR_SLOTS` 不是生成区块（旋钮的标签、分组和默认值都是手写的），但它被三个脚本读：`palette-defaults.mjs` 拿它逐条核对默认值，`theme-surface.mjs` 拿它生成报告里那张旋钮表，测试台拿它数旋钮数量。所以往这个数组里加一个旋钮，报告和校验会跟着一起更新。

## 开发脚本

```sh
python preview/embed_artwork.py                  # 重新内嵌三张图（改图后跑）
node   preview/embed-logo.mjs                    # 重新内嵌官方 logo
python preview/validate_art.py                   # 校验预览页里的 SVG 是否可解析
node   ../analysis/theme-surface.mjs             # 重新生成配色可调范围报告
node   ../analysis/palette-defaults.mjs          # 把 22 个旋钮的默认值和已安装应用逐条比对
node   ../analysis/embed-consumers.mjs           # 重新生成"每个旋钮实测改动哪里"的证据块
node   ../analysis/plugin-guards.mjs             # 模板字符串 / package.json / 生成区块的静态守卫
node   ../analysis/fix-css-backticks.mjs         # 修 STYLE_TEXT 里误写的反引号（--check 只报）`nnode   ../analysis/blue-audit.mjs                 # 有没有哪个颜色是"冻住"的：暖色方案下仍然是蓝的
node   ../analysis/pubcheck.mjs                  # 发布就绪清单（--strict 作为发布闸门，--rename 改包名）
```

`fix-css-backticks.mjs` 存在的理由值得写下来：`STYLE_TEXT` 是模板字符串，而 CSS **注释**里引用一个 CSS 单词时最自然的写法就是加反引号——这一个字符会提前结束字符串，让整个 bundle 解析失败。这件事在这个项目里发生过**五次**，每次的报错位置都离真正的改动很远。守卫脚本会先拦下来，这个脚本负责修。规则本身很简单：**那张样式表里不许出现反引号。**

还有一条给自己的：**不要用 PowerShell 脚本去改源码。** 修上面那个反引号问题时，一个 `$t = [System.IO.File]::ReadAllText((Read-Path $p))` 因为 `Read-Path` 不存在而让 `$t` 保持 `$null`，脚本没中断，接着 `WriteAllText($p, $t)` 就把整个 `test/client.test.mjs`（约 10 万字符）写成了空文件。没有 git、没有备份。最后是从 DSH 自己的会话日志（`~/.dsh/sessions/**/session.v4.jsonl.zstd`，6106 个 zstd 帧，解出 26.9 MB 的 JSONL）里把历次 `write`/`edit` 调用重放出来才恢复的——而且重放会漏掉那些当时用 pwsh 做的修改，所以恢复出来的文件有 17 个断言停留在旧版本。结论：**文本改动一律走 edit/write 工具**（有"文件已变"保护），脚本只用来读取和校验。

`palette-defaults.mjs` 是**会失败的**：它从 `client.js` 里把旋钮表读出来，再从已安装的应用里把这些 token 在两个模式下的实际取值解析出来（`var()` 链也会展开），逐条比对，不一致就以非零码退出。手写 44 个十六进制值而没人核对，是那种"看起来对、其实早就不对了"的典型。

`embed-consumers.mjs --check` 只校验不写：生成区块过期就非零码退出。证据过期比没有证据更糟——面板会理直气壮地说"实测改动 53 处"，而应用早就不用那个 token 了。

三个脚本共用 `analysis/lib/asar-css.mjs` 读归档和样式表（asar 头、`unpacked` 处理、`selector{…}` 扫描、类名哈希还原）。`asar-grep.mjs` 也改用了它。顺带记一个 PowerShell 的坑：给原生命令传空字符串参数会被丢掉，`... "" 6` 会变成 `... 6`，于是 `6` 被当成路径过滤条件，结果是"全归档零匹配"——看起来像工具坏了，其实是调用方式。

`plugin-guards.mjs` 守两件 `node --check` 管不到的事，两件都真的踩过：`STYLE_TEXT` 模板字符串里出现反引号（在中文注释里写 CSS 关键字时最容易犯），以及 `package.json` 被加上 UTF-8 BOM 导致 `JSON.parse` 抛错、整个 profile 解析不了插件。

## 测试

```sh
node dsh-diy-skin/test/client.test.mjs
```

测试台桩掉 `window.__ModuleLoader__`、`react`（含 `useState` / `useEffect` / `useRef` 三个 hook）、`react-dom` 的 `createPortal`、`localStorage`、`window` 事件与一个可选的 `dshPlatform`，捕获真实的 `{ inject, apply }` 并渲染真实注册的插槽组件，因此断言覆盖的是实际发布的代码，而不是它的副本。它还会**像真 React 一样拒绝 hook 数量变化的组件**（见上文那个陷阱）。**74/74 通过。**

覆盖范围：

- 三层 token 都注册、且调色板里每一项都是成对的 alias token；从没调过色的 profile 里，**第三层必须是空的**（"没碰过就不写"）；
- **弹出层材质是不透明的**：三个填充色都必须是六位十六进制（无 alpha），`--dsw-menu-backdrop-filter` 必须是 `none`；
- 金额格式化：单钱包 / 多钱包累加 / 千分位 / 次分级 / 混合币种 / 零余额；
- 账号缺失与读取异常的降级、客户端元数据字段、折叠态与窄侧栏行为；
- **单击刷新 / 双击充值**：单击要等过双击窗口才发读请求，双击**不得**顺带刷新、且在有 `dshPlatform` 时走原生、没有时走 `window.open`；充值页浮层必须带一个可点的返回控件，关闭后插槽回到 `null`；
- **三张内置图被播种成普通条目**：三个 `img.dsd-bg`、都是 data URI、都带完整的可编辑几何；不在编辑态时图层对辅助技术隐藏；
- **编辑态的隔离罩**：关闭时不存在，进入编辑后出现；图层从 `aria-hidden` 变回可交互并抬到 `z-index: 1x`（正则校验，防止以后被改回 0）；图片挂上拖动与滚轮处理器；
- **`Esc` 由图层负责**：面板不在也能退出；退出后两个 window 监听器都被摘掉；
- **拖动不跳、滚轮缩放**：抓在图片中心再拖 64px（1280px 宽 → 5%）后 `x` 恰好 +5、`y` 不动；松手后再移动指针不会继续移动；滚轮一格 ±4vh 且 `preventDefault`（不许滚动背后的应用）；
- **四个角把手 + 对角锚定**：把手位置由 `size × aspect` 推出（`calc(25% - 40vh)` 这种）；拖东南角 160px 后高度 +64px、`aspect` 不变，并且**反算回西北角的绝对坐标仍是 `(0, 240)`**——即"对角不动"是被验证过的，不是被假设的；
- **宽高比进入模型**：`onLoad` 记下 `naturalWidth / naturalHeight`；重复上报同一个比例不产生写入（否则会自己触发自己）；
- **批量滑杆**：拖「全部透明度」后两张图都变成同值、另一个字段不动、滑杆位置被记住；随后单独调其中一张**只改那一张**，全局值不变；
- **面板可拖动**：拖之前不写死位置（沿用样式表的角落锚点），拖之后落位 `{left, top}`；按在关闭按钮上不触发拖动；
- **存下来的背景图**按各自的 size / x / y / opacity / blur 渲染成 `img.dsd-bg`，且不会把播种的三张混进来；
- **v1 → v2 迁移**：v1 里自己的图保留，内置三张按当时的 `showBuiltin` 决定是否补回；
- **拖滑杆会写回 `localStorage`**，空字符串这类脏值被忽略而不是被 `Number('')` 悄悄写成 0；写图片那份时**不带 `colors` 字段**（两个 key 各自独立）；
- **面板是两栏**：左栏仍是原来的编辑器（文件选择器 + 三张播种图），右栏 22 个旋钮 + 两个开关 + 七个预设 + 恢复默认（无覆盖时禁用）；每个旋钮的 `title` 带 token 全名、实测改动处数/包数和采样到的选择器；底部一行给出覆盖率（本栏 22 / 官方 120 / 51 个包写死颜色）；
- **两个角落按钮读的是本插件自己的 `--dsd-chip-*`**：样式表里 `.dsd-chip` 与 `.dsd-balance` 的底色/描边/文字都来自 `--dsd-chip-*`，且**不再含 `--dsw-alias-bg-module-platform`**（这正是"那个旋钮只改了余额按钮"的根因）；四个角落旋钮都在面板里；注入行内值能让色块显示插件层实际画出的颜色；
- **「应用配色」是真切换**：点深色会调用主题服务的 `setTheme('dark')`（而不是只改编辑对象）；随后服务 publish，面板跟着移动标记、把"正在编辑哪一套"切到深色、并**重新读取**颜色而不是吃上一帧的缓存；外部翻转（设置面板、`跟随系统` 下的系统切换）走同一个事件也能反映出来；而"切换编辑哪一套"**不会**碰应用偏好；
- **护眼绿预设**：底色 `#f4f7ee`/`#101710`、气泡 `#e2ecd6`、文字偏绿近黑、强调 `#4f7d3f`/`#8fc47a`，角落按钮跟着变绿，**状态色不写入**（否则"成功"和"选中"会撞色），每个值都是合法成对颜色；
- **余额芯片自报刷新节奏**：就绪态的 tooltip 必须含「每 15 分钟自动刷新 · 单击立即刷新 · 双击充值」；
- **两处挡住图片的系统表面都被关掉**：样式表里必须有 `span[style*='--dsw-specific-sidebar-fill']{background-color:transparent!important}`（原生窗口按钮那条通道的开关）和 `[class*='composerSeat']{background:transparent!important}`（输入框座位）；同时断言本插件**没有**去动应用自己的输入框卡片；
- **编辑用的部件退出窗口拖动区**：`.dsd-layer[data-editing='true']` 与 `.dsd-editor` 都带 `-webkit-app-region:no-drag`；
- **面板不会被停到窗口按钮底下**：标题栏 40px 时把面板往上方拖，落点被夹到 `y=44`；修好之前存下的 `y=6` 在渲染时被拉到 `44`；而**没有**标题栏（macOS/Linux）时同一个 `y=6` 被原样尊重；
- **「更多图片」是一次浏览器跳转**：点击前不打开任何东西，点击后 `window.open` 收到 `https://ai-meme.cdqyfdbymn.me` 且 `target=_blank`；布局是 `2fr 1fr`，两个按钮同为 28px 高，且"添加图片"是实心、"更多图片"是描边；
- **一个旋钮写一对值**：只改浅色时，层里那个 token 的深色是**记录下来的默认值**，不是被编辑传染的值；层里只出现碰过的 token；
- **浅/深开关决定写哪一个**：切到深色后输入框显示的是深色默认值（不是刚敲的浅色值），两边可以分别设；
- **半成品不落盘**：`#41` 只进草稿、层和存储都不动，输入框显示 `#41` 而不是弹回原值；补齐第 6 位才提交；失焦丢弃草稿；
- **调色盘保留 alpha**：`#1d4ed80f` 的旋钮在调色盘里显示 `#1d4ed8`，换成绿色后写进层的是 `#00ff000f`；
- **单个旋钮可以只还原自己**，其余覆盖不受影响；被还原的 token 是**从层里消失**，而不是被写成一份默认值的副本（否则别的皮肤的值永远透不过来）；
- **预设一次写 19 个旋钮值**（含自带皮肤不碰的侧栏与气泡），每个值都是合法成对颜色；写完还能接着单个改；「恢复默认」把层清空、存储清成 `{}`、按钮重新禁用；
- **重启后颜色还在**：启动时读存储并推一次，所以首屏就是对的；存储里的脏 key、非颜色值会被丢掉，下一次写入只保留合法旋钮；
- **关闭插件会收回颜色层**（和自带品牌层一样），否则会留下一套没人能撤销的颜色；
- **无关的 store 变化不重新发布主题**：半成品输入和"选中一张图片"都会触发订阅，但层不重推——这是拖图片时每帧重写几百个行内属性的那道闸。
- **色块显示的是页面上真实的颜色**：行内值优先于 `getComputedStyle`，两者都优先于插件记录的表；`rgb()` / `rgba()` 会被换算成十六进制（含 alpha），而 `color-mix()` 这类换算不出来的值**退回记录的默认值**，不会假装成一个十六进制；用户自己设过的值优先于两者。18 行的读取按主题的 `revision` 缓存了一次，所以拖图片时不会每帧重读 18 遍计算样式。

## 已知限制

- 暗色模式的藏青底色是刻意偏离原有中性色的设计选择；如果你更想要原汁原味的中性灰，删掉 `BRAND_TOKENS` 里 `--dsw-alias-bg-*` 那几个条目即可，只保留交互蓝。
- **配色栏是认得出来的一批，不是 401 个 token。** 这是取舍：能量的是"界面上认得出来的地方"，不是"所有能改的东西"。这些旋钮全部来自实测消费方最多的那批 token（见 [THEME-SURFACE.md](THEME-SURFACE.md) 第 3 节）。想加旋钮就往 `COLOR_SLOTS` 里加一条，报告和校验会跟着更新。
- **只改一种模式时，另一种模式用记录下来的默认值**。能读到的一侧是**页面上真实的颜色**（包括别的皮肤设的），读不到的那一侧只能退到插件记录的表。所以如果你装了第三方皮肤又只改了深色、然后切到浅色，那个 token 的浅色会回到"本插件默认的样子"而不是那个皮肤的样子。两侧都设一次就没有这个问题。
- 余额数字来自 Platform 接口按需拉取，不是实时流，因此可能与你刚充值的金额有几秒到几分钟的偏差；点一下芯片可立即刷新。
- **图片现在真的在应用底下**（`z-index:-1`），代价是它只能出现在应用自己留空的地方。画面主体已经全部让开：应用外框、中间那一列画布、会话列自己的 root，以及**左侧栏**（列本身 + 里面那个 root + Windows 顶部那条标题栏）。**卡片、输入框仍保留各自的不透明底色**——面板浮在壁纸之上本来就是对的，想让它们也透出来就把对应旋钮设成带 alpha 的值（输入框接受 8 位）。另外这一层靠 `[class*='frame']:has([class*='sidebarCol'])`、`[class*='root']:has([class*='newSession'])` 这类选择器认应用的表面，**宿主大改版后这里应当重新核对**（`analysis/theme-surface.mjs` 会重新列出实际的类名与消费方）。
- **侧栏的颜色衬在图片下面，而不是盖在上面。** 第一版是给侧栏加一层 45% 的薄纱：侧栏认得出来，但图片被冲淡了——用户的原话是"薄纱是为了让人能看出侧边栏的存在（应当保留！），但代价是图片显得被盖住了"。两件事其实可以同时成立，只要**把颜色挪到壁纸的另一侧**：侧栏那两层的底色全部透明，改为在**图片层里、所有图片之前**画一块"床"（`.dsd-side`，颜色就是原来的 `--dsw-specific-sidebar-fill`，位置和宽度由 `trackComposerPane` 顺手量出来）。于是：图片保持完整强度，而侧栏与主界面的区别由**图片底下的底色**加上一条**在图片之上的发丝线**（`.dsd-side-line`，1px，用「边框与分隔线」那个旋钮的颜色）承担——图片调到 100% 不透明时，那条线仍然在。Windows 顶部那一条用的是同一个 token，但它既不要床也不要线：那里没有侧栏，只有图片。
  **会话列表底部那条滚动渐隐要关掉。** 它是 `[workspace] .fade`：从透明渐变到侧栏底色，画在图片**之上**，用来让列表滚出视野时淡出。颜色挪到图片下面之后它就多余了，而在它还在的时候，它的不透明末端正好落在两个角落按钮上方——用户看到的就是"按钮上沿有一条分界线"。 应用给输入区留了一小块下边距，座位（seat）的盒子到那里就结束了；只按座位的高度铺遮挡层，正文会从那道缝里露出来（用户报过"输出框下方的正文又露出来了"）。所以带子的高度是 `座位高度 + 座位离窗口底部的距离`，下边缘钉在窗口底部而不是座位底部——图片的第二份也用同一个 `clip-path`，两处始终是同一个矩形。
- **带子的上边缘要整体渐隐，不能只让遮挡层渐隐。** 这是用户报的第二处：输入框上方能看到一条明显的分界线，上下图片颜色不一致。原因是遮挡层必须"大部分不透明"（这样才挡得住正文）但"顶部要软"（否则正文被切成一条硬边），而**半透明的遮挡层会让背后的壁纸透出来，同时上面那份图片副本照样全强度画着**——同一张图在渐隐的 44px 里被画了两次，多出来的那一份就是那条亮线。修法是把遮挡层和图片副本**包进同一个容器、用一条 `mask-image` 一起渐隐**：顶部只有壁纸，下面只有副本，中间按比例互补，加起来永远恰好是一张图。
- **带子只在输入框"贴底"的时候才铺。** 这是用户报的界面级 bug：**开新会话时整页只剩背景图片**。新会话页把输入框摆在页面**正中**，而原来的判断只看"座位有没有、大不大"，没看"在不在底部"——于是那条本该挡住下滚正文的遮挡带，横铺在了整张首屏上。判据现在是**离窗口底部多远**，并且用窗口高度的比例（贴底大约 20px，居中则是几百 px），这样任何分辨率都成立。
- **去白底：改哪个旋钮就存哪个旋钮，原图保留。** 技术核心是**从四边向内漫水填充**：从图片边框开始扩展，只穿过接近白色的像素，所以**主体内部的白色（围裙、眼睛高光）会留下**——这是"填充"和"全局阈值"的全部区别，也是它值得这些代码的原因。填充用**扫描线**实现（每个种子沿本行左右走到底），空白区域只占一个栈位而不是每像素一个，这是"能不能感觉到卡"的分界。
  拖动参数时跑的是**粗一档**（长边 560），所以结果两帧内到手、滑杆是黏在图上的；松手 280ms 之后才跑**全分辨率**那遍，被取代的那遍用序号自己作废，快速拖动不会把旧结果盖上去。
  **这一版最初做成"试看 → 按一下才落盘"，后来那个按钮被删掉了**（理由见下面"原图留下来"那一条）：现在旋钮改动直接写进 `item.key`，全分辨率那遍替换 `src` 并落盘，粗那遍只当屏幕上的临时替身。存成品实测**+61%**，留着原图再翻一倍（数字来自 `analysis/white-keying-cost.py`）。透明区域的 RGB 会被填成纯白：那些像素看不见但**照样要编码**，把旧背景留在透明底下等于为同一份细节付两次钱。
- **A 和 B 终于量了，不是推理的。** 之前我一直说"存原图重算会拖慢启动"，却从没测过。用户问"我们是不是从来没直观对比过"，确实没有，所以补了一条基准测试（`the cut fits the frame budget on a full-size picture`），用一张合成的"照片感"图（1600×1000：带噪声的近白背景 + 主体 + 几条细线；填充的代价取决于"要停几次重开"，平坦的白底测的是最容易的情况）：

  | | 存成品（A，已实现） | 存原图每次重算（B） |
  |---|---|---|
  | 启动代价 | **0 ms** | 每张去白底的图 **~114 ms** → 十六张约 **1.8 s**，**每次启动** |
  | 存储 | 每张 +61% | 不变 |
  | 想改参数 | 得重新添加那张图 | 随时可调 |

  粗那遍（0.2MP）约 30–40 ms，所以拖动是跟手的；全分辨率（1.6MP）大约 100 ms，作为一次主动操作完全没问题——但**乘八、再乘"每次启动"就变成用户会感觉到的东西**，而且它会落在应用自己也在加载的那一秒里。测试里留了两条宽松上限（粗 <400ms、全 <1200ms，后者扣掉 280ms 的静默等待）当护栏，免得以后哪次改动让填充慢一个数量级而没人发现。
- **"应用并保存"这个按钮被删掉了，原图留下来。** 第一版我做成"试看 → 按一下才落盘"，理由是想省存储：落盘之后原图就没用了。用户的回答是"应当保留用户在原图基础上继续调节的权利"——他是对的，而且这不是一个存储问题：**取消那个按钮省下的不是空间，是权限**。
  现在的模型是：一张被切过的图身上有两样东西——`src`（切好的，用来画）和 `original`（当初导入的那份，用来重切）。旋钮改动直接写进 `item.key`，**没有确认步骤**；粗那遍只当屏幕上的临时替身，全分辨率那遍才替换 `src` 并落盘（防抖 280ms）。取消勾选就把 `src` 换回 `original` 并丢掉 `key`，那份副本也就释放了。
  代价是**每张切过的图要存两份**（约 +122%）。**这个代价后来被证明远没有我当时说的那么要紧**——见下面关于上限的那一条：真实的可用空间是 32 MB 量级，满十六张图连备份大约占 13%，每次保存要给这 4 MB 做一次序列化，实测 **6.7 ms**。
- **两个手工修正旋钮，对着的正是"复杂边缘判定不准"。** 用户看过第一版之后的反馈是：边缘复杂的地方（头发、蕾丝、气泡框）切得不干净。这不是容差调不好，而是**有两类相反的误差**，一个滑杆治不了两种病：
  - **收边 / 扩边（±3px）**：留下白边就往里收，啃进主体就往外放。实现是掩膜的一遍**膨胀 / 腐蚀**（3×3），每遍移动一个整像素。腐蚀那一版我写错过：第一版写成"没有掩膜邻居就置 1"，等于把整张图填满——正确的腐蚀是"掩膜像素只有在**邻居全是掩膜**时才留下"。
  - **柔和边缘被砍掉了。** 我做过第三个旋钮：alpha 不再 0/255 两档，而是按"有多白"算出来。用户的判词是"纯纯副作用"——背景稍微不均匀，它就留下一层很淡的、到处都是的影，而真正的复杂边缘该不该留白本来就该由**收边**决定。**一个能看出副作用的旋钮不如没有旋钮**，所以它连同代码一起删掉了，而不是留一个默认关着的开关。
  两个旋钮和容差是三路独立的输入，改任一个都会带上另外两个当前的值重算（`requestKeyPreview` 里先合并再排队）。
- **上限是量出来的，不是引用的——而量出来之后，我原来的说法错了 6 倍。** 我在面板和文档里都写过"Chromium 通常 5 MB"，那是**没有验证过的数字**。用户当场指出："有办法确定一个真实的上限吗，我们不能拿一个可能不存在或者不准确的限额欺骗用户。"
  浏览器不公开这个配额，**唯一诚实的办法是真的去写，写到它拒绝为止**。所以读数条上有一个按钮：二分查找（约九次写入，每次比上一次大一倍、互相覆盖，所以峰值就是一个字符串，结束时一次 `removeItem` 清掉），把最大的**写得进去**的长度记下来，存进 `dsd:quota:v1`——配额是来源的属性，不是会话的属性，量一次就够，之后按钮变成「重测」。
  它是**用户主动点的**，因为测量不是免费的：那零点几秒里存储是真的满的，任何想写数据的东西（包括本插件自己）会被拒绝一次。这条写在按钮的 tooltip 里，不藏在代码里。
  单位用**字符**而不是字节：读数条本来就这么记账，所以无论浏览器内部乘几，显示的百分比都是准的；没测之前面板说的是"上限未测"，**不编一个数**。
  **实测结果：31.9 MB（33,488,896 字符）。** 我猜的 5 MB 差了 6.4 倍。这个数字本身还说明了一件事：**我之前所有关于"存储紧张"的取舍叙述都是错的**——留原图、存两份、+61% / +122% 这些百分比虽然都对，但它们的分母根本不是我以为的那个。八张图连备份约 2.9 MB，占 **9%**。教训不是"要量"，而是**我拿一个没量过的数当成约束，然后在它上面做了一串设计决定**。
  读数条现在回答用户真正问的两个问题：**我塞进去的图占了多少**（图片 = 原图 + 备份）、**还剩多少**（余量 = 上限 − 本插件占用 − 应用其它数据，带百分比）。完整拆分（其中原图备份多少、本插件其它数据多少、应用其它数据多少、上限多少）在那一行的 tooltip 里。
  按钮不会消失——第一版量完就把按钮藏起来，用户的评价是"然后按钮消失，什么都做不了了"；现在它变成「重测」，而问题变成了这一行有没有回答"还剩多少"。
- **上限从 8 放宽到 16。** 定 8 的时候我以为存储紧张（错，见上），所以它一直是个"空间"决定；现在理由只剩编辑面板的长度，那就不该拦着人。满十六张、每张都留备份的情况下：payload **4.07 MB**（占 32 MB 上限的 13%），每次保存的序列化 **6.7 ms**（实测，`JSON.stringify` 整个列表——localStorage 没有局部写，改一张要重写全部）。这两个数都在"感觉不到"的量级，所以放宽是安全的；真正会先撑不住的其实是面板的滚动长度，不是存储。
- **存储用量是读出来的，不是猜的。** 面板报的是能知道的东西：本插件占了多少、同一存储里其它数据占了多少（按浏览器记账的方式算：UTF-16 码元，而 data URI 是 ASCII，所以一个码元就是一个字符）。上限到了会明确提示（含壁纸在内最多 16 张），不会静默失败。
- **面板会挡住中间的图，所以图的控制得能跟着图走。** 用户的要求：把面板拖到下面藏起来，以便在屏幕中央操作图片——那"调图"这件事就不能只住在面板里。于是**右键图片**会在它旁边开一个小窗口，内容与面板里那张图的一段**完全一样**（同一个 `PictureControls` 组件，写两遍一定会走样）。位置在渲染时用图片自己的 `getBoundingClientRect()` 量，所以拖动之后它跟着走；量不到（测试环境、还没挂载）就退回左上角，而不是拿模型里的百分比猜一个屏幕坐标。Esc 一次只关一层：先小窗口，再退出编辑——把两层一起关掉，这个小窗口就成了陷阱。
- **大小和位置的三条滑杆彻底删掉了，连小窗口里也没有。** 既然拖拽和滚轮已经能直接改，它们只是在拉长面板（用户的原话是"背景菜单的滚动长度也会有所缓解"）；后来用户又明确了一次"可以直接删掉了，用手调整的功能已够用"。代价要写清楚：**现在没有任何输入框能精确设定尺寸或坐标**，只有拖动、滚轮、四角拉伸。
- **"操作哪张图，哪张图的框就该亮着"——一个动作，一种含义。** 用户报的两件事其实是同一件：操作新图片时，上一张的右键小窗口该消失；面板里正在操作的那一行该亮起来（列表有十六张时还该滚进视野）。所以它们合成一个 `touchPicture(id)`：面板的摇杆、小窗口、直接在画布上拖/滚/拉角、去白底开关——所有"动这张图"的入口都调它，它做两件事：把 `selected` 指过去（行亮、画布上的虚线框跟过去、必要时滚进视野），以及**关掉别的图片的小窗口**（同 id 的留着，那就是你正在操作的那张）。一个动作只有一种含义，才不会出现"我明明在改 B，A 的窗口还挂在那里"。
- **输入框上方那块白色：带子里的第二份图，把壁纸画成了贴纸。** 用户的猜测很准（"估计还是图片放在具体哪个高度的问题"）。带子（`.dsd-band`）里有一份图片副本，用来盖住输入框那一条里应用自己画的不透明背景；它给**每一张**图都用了贴纸样式（`pictureStyle`：`height: size vh` + `left/top` 百分比），于是一张"整图壁纸"在那里变成窗口中间一个 60vh 的方框，其余地方露出 veil 的纯底色——浅色模式下就是**一整块白**。只有贴纸时看不出来，因为那时底色和应用自己的背景同色；一放壁纸，两者的差别就是那块白。修法：带子里按 `item.full` 分别用 `fullStyle` / `pictureStyle`，并给副本加一个**独有的** `data-band-item`（不能复用 `data-item-id`：小窗口正是靠后者去问"这张图真实的框在哪"，而每张图有两个副本）。
- **动图：宁可文件大，也不要静悄悄变成静图。** 导入管线本来会把"长边超过 1600 或大于 400 KB"的图过一遍 canvas（缩到 1600px 的 WebP）——而 canvas 只有一帧，所以一张 GIF 会**悄无声息地变成静图**，用户只会觉得"我加的动图怎么不动了"。修法是在进 canvas 之前分流：`data:image/gif` 开头的一律**原样保存**，不缩放、不重编码。更大的文件是这两个结果里较好的那个，何况现在知道上限是 32 MB。
  配套的一半是诚实：**动图的"去白底"开关是禁用的**（title 写原因："动图每一帧都要处理"）。给一个按下去就把动画压平的开关，比没有这个开关更坏。
  已知边界：只有 GIF 能从 data URI 前缀认出来；**动图 WebP** 和静态 WebP 长得一样，所以它只在"小到不需要过 canvas"时才保住动画。这条写在函数的注释里，不假装完整。
- **小窗口的四次修正，都是"它站在别人的地盘上"这一类问题。** 用户一次报了三件：① 底色不透明（半透明的 popover 材质让底下的文字透上来）；② 面板应该盖在小窗口上方（原来小窗口在面板上面）；③ 图片拖到最右时窗口压在自己的图上；④ 壁纸的小窗口开在右上角，正好压住窗口的最小化/关闭按钮。
  ①② 是取值问题：小窗口改用 `--dsw-alias-bg-base`（面板同款，不透明）并把 `z-index` 从 1003 降到 **1001**，低于面板的 1002。
  ③ 是位置算法：从"永远放右边"改成**先右、再左、再下、再上**，每一种都要真的放得下才用——图片贴到右边缘时，窗口就到它左边去；两边都不够就挪到上下。位置在渲染时用图片自己的 `getBoundingClientRect()` 量，所以跟着图片走。
  ④ 是默认位置：壁纸**没有"旁边"**（它就是整个窗口），所以它的窗口固定在**左侧垂直居中**——聊天窗口上唯一一块既没有文字、也没有窗口按钮的地方。
  另外小窗口现在可以**拖**（拖标题栏），拖过之后那个位置一直有效到关闭为止：人是故意挪的。
- **"点完重测没有反应"是反馈缺失。** 重测之后那行数字几乎不变（本来就知道上限了），所以看起来像什么都没发生。现在按钮点完会变成「**已刷新**」，三秒后变回「重测」——用按钮自己说话，而不是再往面板里塞一行字（那正是上一轮把读数挤出视口的做法）。
- **那一行和它的 tooltip 是同一笔账的两端。** 行上只有两个数（图片、余量），tooltip 里是四个数，中间少了"已用"这一项，所以看起来像两组无关的读数。现在 tooltip 把算式写全：`图片 0.7 MB（含原图备份 0.4 MB）+ 本插件其它 3 KB + 应用其它 62 KB = 已用 0.8 MB；上限 31.9 MB（实测）− 已用 = 余量 31.1 MB`。
- **提示文案只写用户需要的那一句。** 用户的批注是"toolkit 不用写那么多，只写用户有必要看到的东西"。我原来的 tooltip 里混了三类东西：使用者需要的信息（上限多少、备份占多少）、只对维护者有意义的信息（"探针"、"二分查找"、"如果这时应用要写数据那一次可能失败"）、以及我自己的判断过程。第三类全删，第二类压缩成一句真正的代价说明（"量的时候会短暂占满本地存储，然后立刻恢复"），第一类只留数字。同样被压缩的还有面板里的说明段落：颜色那两条从三行压到一行，编辑态的引导从两句压到一句。
- **"重测之后读数不见了"不是显示问题，是布局问题。** 用户报的是"点击重测应该是刷新前面的值，而不是跳转到实测上限约 31.9 MB，必须关闭背景按钮再打开才能恢复"。原因：测量成功后会往面板末尾塞一条 notice，而面板是"头部固定 + 身体滚动"的纵向 flex——notice 一进来就挤掉身体的高度，读数那一行（身体里的最后一项）被推出可视区；关闭再打开会重置滚动位置，所以看起来像"恢复了"。修法有两层：**测量成功后不再发 notice**（那行自己就从"上限未测"变成了"余量 31.1 MB（97%）"，那才是用户要看的），以及**notice 改成绝对定位**（状态提示不该让面板重排）。
- **带子的位置要跟着页面变，而且量不到座位时必须四边清零。** 尺寸观察者只在"大小变了"时触发；**从一个页面走到另一个页面**（比如打开插件页）时座位消失、什么都没有 resize，于是带子留在原地——一块不透明的面板压在下一页的底部，指针还能穿过去点到底下的按钮，用户只能靠猜。而且它看起来是"偶发"的：第二次进来时某个 resize 已经顺手修正了它。修法有三层：① 用 `MutationObserver` 盯住 `body`（合并到每帧一次写入，所以对话再忙也只是一次查询）；② 量不到座位时**四个变量全部清零**，而不是只清高度——因为遮挡层的高度是 `pane-bottom + pane-height`，残留的 bottom 会在下一页留下一整条不透明带；③ `--dsd-pane-left` 永远不小于侧栏右边缘，这样任何一次过期或异常的测量都不可能横跨过去盖住左下角那两个按钮。
- **原生标题栏按钮压住了应用的图片预览关闭键——而且点错会关掉整个应用。** 预览的关闭键是 `position:fixed; top:20px; right:20px; 36×36`，Windows 的标题栏条是 40px 高，所以它一直有一半在原生按钮底下，只是以前那条带子不透明、看不出来。**页面里的任何东西都盖不过原生覆盖层**，只能把按钮往下挪。
  第一版用 CSS 猜选择器，**没生效**：那个按钮所在的样式表在归档里是分块的，选择器读不全——`maskDrop` 其实是我从一段被截断的文本里推断出来的名字，它并不存在。
  现在改成**在 JS 里按形状认**（`trackOverlayChrome`）：`position:fixed` + `top/right: 20px` + `36×36`。这个界面里没有第二个控件是这个形状，所以不需要知道类名。`MutationObserver` 盯着 `body` 的直接子节点（应用的浮层都是 portal 到 `body` 的），浮层一出现就扫一遍；已经挪过的不会再叠加（挪过之后计算出来的 `top` 就是 60px，签名不再匹配）。没有标题栏的平台整段是空操作。
- **整图壁纸是同一个模型里的 `full: true`。** 它和贴纸共用一份列表，区别只在渲染：铺满视口、`object-fit: cover`、没有边缘蒙版、没有位置和大小可言（所以不能拖、没有四角把手，编辑器里也只给透明度和模糊两个滑杆）。它靠**渲染顺序**而不是 `z-index` 垫在最下面：基图先画，贴纸后画——模型里的先后顺序是用户添加的顺序，而"壁纸在底下"不该由它决定。同一时间只保留一张：再添加一张会替换掉原来那张（否则第二张永远看不见，读起来像"添加没反应"）。
- 图片层、编辑器、充值页宿主都 portal 到 `document.body`，因此**在每一页都在**（包括「新会话」和「插件」页）。若某个宿主拿不到 `react-dom`（`createPortal` 不可用），四者会退回就地渲染：图片会落进 `shell.overlay` 那一层（`z-index: 20`），看起来会盖住侧栏。
- 拉伸现在用的是**四个角**的把手，对角固定。代价是每张图必须在模型里存一个 `aspect`（由图片解码时测出）。如果某张图的 `src` 是不可解码的（比如坏掉的 data URI），`aspect` 会停在默认值 `1`，那张图的把手位置和缩放比例就会偏——但拖动本身不会坏。
- 背景图存在**浏览器级** `localStorage` 里，所以换一个浏览器/Web 端看就是另一套；同一台机器的桌面应用内是持久的。不写 profile，因此卸载插件不会顺手删掉你的图。**面板位置和两个全局滑杆的值也存在同一份状态里。**
- 自己加的图会被压到长边 1600px 的 webp，超大图的细节会有损；这是为了不撑爆配额，属于刻意取舍。**动图是例外**：GIF 原样保存、不缩放，所以它可能明显更大（一张动图占几 MB 很正常）。
- **动图不能去白底。** 去白底跑在 canvas 上，而 canvas 只有一帧，硬做会把动图压成静图；所以那个开关对 GIF 是禁用的，鼠标停上去写着原因。
- **没有输入框能精确设定大小和坐标。** 这是刻意的：拖拽、滚轮、四角拉伸已经够用，三条滑杆只是在拉长面板（见下文）。要"精确到 50vh"目前没有入口。
- **只在 Windows + 已安装的这个 DSH 版本上验证过。** 标题栏那条修正只在 `data-windows-titlebar` 存在时生效，其他平台是空操作；macOS / Linux 上"预览关闭键被窗口按钮压住"这个问题是否存在、以及是否已经解决，**未经验证**。
- **深色模式下，浅色底图去白底后仍可能留一点边。** 这是透明度数学的问题（半透明像素和深色背景混色），不是算法能完全消除的；浅色图配深色背景时更明显。
- 编辑期间整块界面被隔离罩挡住——这是你要的效果，但代价是**侧栏上那个「背景」按钮也点不到了**，退出只能靠面板的 ✕ 或 `Esc`（后者由图层注册，面板即使出问题也仍然有效）。面板本身可以拖到任何位置，所以"它挡住我要调的地方"这条已经解决。
- 「双击充值」走的是宿主原生 `WebContentsView`。若某个宿主的 `dshPlatform` 行为与官方 `ui-settings-account` 不一致，失败时留在状态页并给「重试 / 在浏览器打开」，不会把界面卡住。
- 弹出层材质被全局改成不透明后，**官方所有 `MenuSurface` 菜单都不再是毛玻璃**。这是修"看不清"的直接代价；不喜欢就删掉 `MATERIAL_TOKENS` 那一层（它和调色板是独立的两个 `overrideTokens` source）。
- 表情包图片自带文字气泡，作为背景时会带上那行字。觉得太抢眼就删掉那个条目，或在编辑器里压低它的透明度。
- 图片和 logo 都是内嵌的 base64，`client.js` 因此约 **482 KB**；这是「服务端不伺服包内静态文件」的必然代价（官方 logo 的那 3.4 KB path 同理）。

## 发布（作为一个 DSH 插件）

这个包是**按可发布来写的**，不是一个只在本机跑得起来的草稿。"可发布"在这里是一份可以机械校验的清单，`analysis/pubcheck.mjs` 就是那份清单：

```sh
node analysis/pubcheck.mjs            # 出报告；结构性错误才非零退出
node analysis/pubcheck.mjs --strict   # 发布闸门：还有待办项就非零退出
```

它真正在防的几件事，都是"错了会很难查"的那种：

- **包名必须四处一致。** 浏览器半在 `window.__ModuleLoader__.load({ id })` 里用这个 id 注册自己，`PLUGIN_ID` 用它给主题层命名，`cordis.patch.yml` 的插件行也写着它。任何一处不一致，症状是**插件静默不挂载**——没有报错，只是什么都没发生。
- **不许有 `@deepseek-ai/*` 依赖。** 尤其是 `@deepseek-ai/schemastery`：它没有跟随 DSH 安装一起发布，声明它会让 profile 的包管理器去 registry 找一个可能和运行版本对不上的版本，而**一个坏掉的 profile 依赖会让整个 profile 起不来**。所以本插件声明零依赖，所有取值写死在代码里，可调项都在这个 README 里。
- **`files` 白名单**必须覆盖全部运行时文件，且不许把 `test/`、`preview/`、`analysis/` 发出去。
- **不许泄漏开发机的绝对路径**（这条真的抓到过两次：一次是安装说明里写着我的工作目录，另一次是这句说明本身把那个路径当例子写了进来——扫文档的检查，最容易被解释它的那段话绊倒）。
- **README 里引用的测试数量必须和测试文件对上**——那是文档里唯一一个读者无法凭阅读验证的数字。

当前状态：**0 个结构性错误，3 个发布前待办**。清单在这里，连同每项归谁：

### 这个包的形状

- `client.js` 约 **482 KB**，其中绝大部分是内嵌的三张图的 base64。它是整个浏览器半，也是整个 UI——宿主半（`index.js`）是空的，只为了让 Loader 有一行可解析的宿主插件。

### 加载失败时的排查入口

最直接的一步是查启动清单里有没有本插件：

```js
JSON.stringify(window.__DSH_BOOT__).includes('dsh-diy-skin')
```

返回 `false` 就说明宿主半侧没挂载，后面一切都不用查了（历史上就是 `name` 写了目录而非入口文件）。

`apply` 还会往控制台打两行标记，但界面走 Electron 的 `dsh-app://` 载体时它们落在主进程日志而不是页面控制台，所以**以启动清单为准**：

```
[deepseek-decor] client half loaded
[deepseek-decor] brand palette applied (50 tokens)
[deepseek-decor] popup material made opaque (4 tokens)
```

### 为什么 `theme` 必须写进 inject

这一条我一开始判断反了，值得记下来。我原以为 `inject` 列出的服务是硬依赖——缺一个就静默不激活——于是把它缩减成三项来"加固"。

**实际上恰好相反**：在这个框架里，把服务名放进 `inject` 正是**等待该服务就绪**的方式。官方 `settings-account` 客户端就声明了 `["slots","locale","remote","remote.account","theme","configForms"]`。我把 `theme` 删掉后，`apply` 跑得比主题服务注册更早，`ctx.theme` 还是空的，于是调色板层从未注册——**界面颜色完全没变，且没有任何报错**。

所以正确的写法是**声明** `theme` / `remote.account`，同时在调用处仍按需解析（`ctx.remote.account` 可能与 `remote` 不同时存在），做到"等到就绪"与"缺了也不崩"两者兼顾。

### 插槽选择的实测经验

- **`sidebar.toggle.badge` 是单占用者**。图片层和折叠徽标同时注册进这个插槽时，只有先注册的生效，另一个**被静默丢弃**。图片层因此不在这个插槽里——它现在是 root 作用域 portal 到 `document.body` 的一个固定层。
- **CSS 自定义属性要同时声明在 `:root` 和 `body`**。主题 presenter 把 alias token 作为**内联自定义属性写在 `body` 上**（`body[style="--dsw-alias-*: …"]`），而 `body` 作用域的声明优先级高于 `:root`。只写 `:root` 时，落在 body 上的属性会遮蔽它。按下不再需要这条：三张图改成条目后，data URI 是 `<img src>` 而不是自定义属性。
- **`shell.overlay` 是 root 作用域的列表插槽**，所在层 `z-index:20; pointer-events:none`，而 `>*{pointer-events:auto}`。它适合放"全视口但不常驻"的东西：组件关闭时返回 `null`，插槽包装元素就是 0 尺寸，不挡任何点击。**但它不适合当背景**：那一层在侧栏之上，图片放进去会盖住界面。背景层要 portal 到 `document.body` 才落在 `z-index: 0`。
- **帧内赢不了标题栏**。`overlayLayer` 最高 `z-index: 20`，而 Windows 标题栏是应用自己的 DOM（`.frame:before` 画拖拽带，高度由 `--dsh-windows-titlebar-height` 公布）。任何要与标题栏共存的全屏浮层都得 portal 到 body 并用这个变量留白。
- **插槽占用者要是"纯元素工厂"**。注册进插槽的组件如果是 `useState` 的拥有者，在测试台里直接调用它会崩（hook 需要 React 的渲染上下文）。本插件所有注册点都包了一层薄壳（`function X(){ return h(Real) }`），hook 只经 React 自己的渲染进入。
- **一次 `loadPlugin` 一套 React 桩**。测试台每次 `loadPlugin` 都会新建 harness，所以第二次加载的组件必须用**它自己的** `render` 走一遍——混用两个实例会让 hook 拥有者对不上，报的却是莫名其妙的 `Cannot read properties of undefined`。
- **hook 不能在提前返回之后**。这是本插件唯一一次造成"界面卡死、无法退出"的事故，详见 [第 3 节那个陷阱](#一个把面板彻底搞没了的-react-陷阱)。规则很简单：组件里所有 hook 都写在第一个 `return` 之前，副作用该由"永远挂载的那个组件"承担。测试台现在会强制这条规则。
- **模板字符串里的 CSS 注释不能出现反引号**。`STYLE_TEXT` 是一个模板字符串，注释里写 `` `fixed` `` 会直接把它闭合掉——我这次就这么踩了两回，症状是模块整段语法错误、测试全红。`node --check` 是发现它的最快方式。
